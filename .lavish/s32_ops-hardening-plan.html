02

Coverage — the full operational taxonomy

Direct answer to "does this cover every operational metric a lead would capture?" — the first draft did not. It covered the LLM-app signals (latency, errors, cost, quality, security, delivery) well, but a staff/lead reviewer would immediately flag three gaps: saturation (the 4th Golden Signal), data freshness (the exact failure class that already took Explore down in prod), and product / adoption. The deck above now carries all three. Here is the complete set, mapped to the frameworks a lead expects — Google's Four Golden Signals, USE/RED, plus the data- and product-specific layers a served AI app needs on top.

Two tiers, so "complete" stays shippable

Tier 1 — Postgres-native (ships in W0): everything computable from query_runs, events, answer_feedback and the new ops tables — latency, errors, cost, traffic, product, quality, denials, SLOs, plus data freshness (a pipeline-run write) and Aurora cold-starts counted from the existing db_warming 503s (an in-app signal, zero AWS calls). Tier 2 — CloudWatch pull (folds into W2): infra saturation — App Runner CPU/mem, Aurora ACU/connections, CloudFront cache-hit — via one boto3 GetMetricData behind an IAM read grant on the backend role, cached server-side. The deck renders Tier 1 alone if Tier 2 is off — no metrics vendor anywhere.

How every outcome reaches the deck

One principle: every hardening result becomes a row in Postgres, and the Ops tab reads a single pre-aggregated table (ops_rollup, Q3) — so it renders fast and stays up even when Logfire or the AWS APIs are down. The refresh job behind the rollup does the heavy aggregation and the one Tier-2 CloudWatch pull, off the request path. Deep traces still go to Logfire for developer debugging. The write-paths:

W0 builds the frame and the endpoint first; W1–W4 each fill in their tables and light their panels. The dashboard degrades gracefully — a panel with no rows shows "no data yet", never an error.

W1 Reliability — retries, degraded mode, load test

    
The cheapest, highest-embarrassment fix. A single model_factory injects a timeout + jittered exponential backoff into every Agent, replacing the bare Agent(f"{provider}:{model}") the audit found copy-pasted at all six sites. On final failure the caller returns a degraded answer and stamps status='degraded' — never a 502/500. The backend→agent httpx hop gets the same policy. A k6 harness produces the first-ever load numbers.

  • agent_client.py: bounded retry around the backend→agent call; on exhaustion emit a proper error/degraded SSE frame, not a 502.

08
Honest constraints — where the s07 plan needs correcting

  
The audit surfaced four places where the parent plan's assumptions don't survive contact with this codebase. Naming them is the senior move.

  

    

      
1 · App Runner has no traffic split

      
s07 says "canary (App Runner traffic split or ECS blue/green)". App Runner offers neither — it's an all-at-once managed replace, and there's no aws_ecs_service (ECS is jobs-only). Real weighted canary means putting backend-api behind ALB+ECS — weeks of work that fights the scale-to-zero cost design. So W4 records every deploy and ships a one-command manual rollback — automatic alarm-gated rollback is deferred (decision Q1).

    

    

      
2 · The alarms can't notify anyone

      
All 3 CloudWatch alarms publish to SNS topics whose email subscriptions were never confirmed (an account-level issue, per s12 notes). So the rollback trigger can't depend on SNS delivery — W4 polls the alarm state via the API instead. Fixing SNS for human alerting is a parallel, non-blocking chore.

    

    

      
3 · Cost is cache-dominated, so pricing must be too

      
Nominal input_tokens massively overstates spend — most are cache hits (~⅙ real cost). A flat price-per-token would make the cost tile wrong by 6×. W2's pricing.py reads cache-hit vs cache-miss tokens separately (currently buried in the trace jsonb — 0031 promotes them to columns).

    

    

      
4 · The data is public — so PII scope is narrow

      
The marts are public NSW property records; the only PII surface is the free-text question a user types (persisted to query_runs/messages). That argues for a light regex scrub + Logfire's built-in scrubber over a heavyweight Presidio pipeline — unless the résumé keyword matters more than the fit (decision Q4).
