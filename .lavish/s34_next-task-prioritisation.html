P0 · Switching Logfire on — dev and prod

No code changes anywhere. Compose already forwards the variable and Terraform already plumbs the secret ARN into both App Runner services — the value is the only missing piece. I can't do this part for you: it needs a token minted under your own Logfire account, and the prod half needs an SSO login only you can complete.

Local

~5 minutes

  1. At logfire.pydantic.dev, create a project and generate a write token (Settings → Write tokens). A read token will not work.
  2. Put it in .env — the key already exists at line 12, currently empty:
# .env:12
LOGFIRE_TOKEN=<your-write-token>
  1. Rebuild just the two services that emit spans:
docker compose up -d --build --no-deps \
  backend-api data-agent
  1. Ask a question in the app, then open the Logfire UI. You should see one trace spanning both services — the backend forwards a W3C traceparent on the agent hop, so the chat is a single linked waterfall rather than two orphans.
Verify it took: docker exec data-qa-agent-data-agent-1 printenv LOGFIRE_TOKEN should echo the token. That exact check is how the audit proved it was empty.

Prod (AWS)

~10 minutes · needs your SSO session

  1. Refresh SSO — I hit an expired session trying to read the secret, so this is confirmed necessary:
aws sso login --profile data-qa
  1. Overwrite the Terraform placeholder. It currently holds the literal string REPLACE_ME_VIA_CLI, and ignore_changes means your real value survives future terraform apply runs:
aws secretsmanager put-secret-value \
  --profile data-qa --region ap-southeast-2 \
  --secret-id data-qa/logfire-token \
  --secret-string '<your-write-token>'
  1. App Runner reads secrets at instance launch, so force a redeploy of both services — backend-api and data-agent:
aws apprunner start-deployment \
  --profile data-qa --region ap-southeast-2 \
  --service-arn <service-arn>
Same token, or two? One project keeps both services in one trace, which is the whole point of the traceparent plumbing. Use the same token for both.

Full procedure is already written up in docs/runbook.md § "Turning tracing on (first-time setup)" — the audit confirmed the commands there are correct.

Two things you didn't ask about

The agent cannot hold a conversation

Every /ask runs from a cold start. There is no message_history anywhere in sandbox_agent.py; the payload carries only question, user and dataset_slug. conversation_id groups messages for the sidebar UI and nothing else — prior turns are never replayed into the model. The pgvector memory that does persist is long-term preferences, not dialogue.

So "now break that down by suburb" doesn't work, in an app whose pitch is a conversational data agent. The risk isn't the matrix — it's that this is precisely what someone does thirty seconds into a live demo, and it's the second question they'll ask.

The sandbox default fails open, not closed

The hardened Pyodide/WASM sandbox is what actually runs — but only because docker-compose.yml and apprunner.tf both explicitly set SANDBOX_RUNTIME=pyodide. The bare code default in config.py is the weaker subprocess runner, whose own docstring says it is "NOT a hard isolation boundary against a determined escape."

Today's deployments are covered, so this isn't urgent. But you talk about containment as a design principle — "the agent physically cannot…" — and security-by-environment-override undercuts that story if an interviewer opens config.py. Flipping the default is a one-line change.
