One identity change, three new front doors

Build instructions for a coding agent. Everything downstream of get_current_user already works for a machine caller — /ask is synchronous, RLS scopes on app.users.id, and query_runs.channel is deliberately free-text "so new channels (slack, mobile) need no schema change." The only thing missing is a way for a non-human to become an app.users row. That's rung 0; the three surfaces are thin adapters on top.

Identity model — how everyone else actually does this

A bot user with its own grants. Channel membership is the boundary.

You asked how other teams get a Slack agent working, and said you'd rather have a bot user with access to property data than impersonate a person. That's the mainstream pattern, and for this dataset it's the right one. My earlier act-as recommendation was over-engineered for what you're actually building — property market data isn't per-person confidential the way a CRM or an HR system is.

The three patterns in the wild

PatternWho uses itCost
Bot-scoped identity yours Most internal data/analytics bots. The bot holds a service identity with defined grants; you control who can ask by controlling who's in the channel. No per-person scoping inside a channel.
Slack OAuth user_scope Third-party SaaS integrations (Drive, Notion) where each person authorises individually and the app acts with their token. An OAuth consent per user; heavy for an internal tool.
Account linking Bot identity plus an explicit /link flow mapping Slack user → app user. A linking flow, a mapping table, and a support burden.
What makes the bot pattern defensible rather than lazy — and this is the part worth doing properly, because it's the difference between a shortcut and a stated architecture:

1. One service account per surface, narrowly granted. Not one global bot key. The Slack account gets grants on the property datasets only, via the existing dataset_access table. The scope is data you'd be comfortable with everyone in that channel seeing — because that is now literally the rule.
2. Record who asked, even though it doesn't change what they see. Put the Slack user id and channel in the query_runs audit trail. Accountability and authorisation are different properties; you're consciously trading the second, so keep the first.
3. Write the boundary down. "Channel membership is the access control for this surface" belongs in the README as a decision. Unstated, it reads as an oversight; stated, it's a design with a known trade-off — which is the answer an interviewer is actually probing for.

Consequence for the build: no act-as header, no subjects table, no allow_act_as flag in migration 0032. Shipping schema nobody reads yet is its own smell, and this repo adds columns with ADD COLUMN IF NOT EXISTS constantly — delegation gets its own migration on the day it's needed. The delegation design is preserved at the bottom of this page as the documented upgrade path.

CREATE TABLE IF NOT EXISTS app.service_accounts (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     uuid NOT NULL REFERENCES app.users(id) ON DELETE CASCADE,
  name        text NOT NULL,
  key_id      text NOT NULL UNIQUE,   -- public half, safe to log
  key_hash    text NOT NULL,          -- sha256 hex of the secret half
  surface     text NOT NULL CHECK (surface IN ('webhook','slack','mcp')),
  created_at  timestamptz NOT NULL DEFAULT now(),
  last_used_at timestamptz,
  revoked_at  timestamptz
);

GRANT SELECT, INSERT, UPDATE, DELETE ON
  app.service_accounts TO app_user;

One table, not two — no delegation schema until delegation exists. surface pins a key to one front door, so a leaked Slack key can't drive the MCP endpoint. Grant each account's datasets through the existing app.dataset_access rows; the bot is a user, so that machinery already works.

Do not grant these tables to agent_ro

The agent writes model-authored SQL. It must never be able to SELECT key_hash, even hashed. Omitting the grant is the control — do not add an RLS policy and assume that's enough.

2 · Key format and verification

new file — services/backend-api/app/service_auth.py

import hashlib, secrets

PREFIX = "dpk_"  # data-pilot key

def mint_key() -> tuple[str, str, str]:
    """Return (full_key, key_id, key_hash). The full key is shown ONCE."""
    key_id = secrets.token_hex(6)             # 12 chars, public, indexed
    secret = secrets.token_urlsafe(32)         # 256 bits of entropy
    full = f"{PREFIX}{key_id}_{secret}"
    return full, key_id, hashlib.sha256(secret.encode()).hexdigest()

def split_key(token: str) -> tuple[str, str] | None:
    """dpk_<key_id>_<secret> -> (key_id, secret), or None if malformed."""
    if not token.startswith(PREFIX):
        return None
    rest = token[len(PREFIX):]
    key_id, _, secret = rest.partition("_")
    return (key_id, secret) if key_id and secret else None

def verify(secret: str, key_hash: str) -> bool:
    computed = hashlib.sha256(secret.encode()).hexdigest()
    return secrets.compare_digest(computed, key_hash)
Why SHA-256 and not bcrypt/argon2 — state this in the docstring so a reviewer doesn't read it as laziness: the secret is 256 bits of CSPRNG output, not a human-chosen password. There is no dictionary to attack, so a deliberately slow KDF buys no security and costs latency on every single request. This is the same reasoning GitHub and Stripe apply to API tokens. Password hashing rules do not transfer to high-entropy tokens.

Rungs 1–3 · The surfaces

rung 1

Webhook

~0.5 day

Prove the auth works, with the least new surface area. Another server POSTs a question with its key; the answer is POSTed back to a callback URL.

new file — services/backend-api/app/routers/integrations.py · register in main.py alongside the existing routers

  • POST /integrations/webhook/ask — bearer key in the header (the caller is a server, so TLS + bearer is sufficient; HMAC is only needed when the secret can't ride in a header, which is rung 2's problem).
  • Return 202 Accepted immediately with a request id, then deliver via BackgroundTasks. /ask can legitimately run 120s; no sane caller holds a connection that long.
  • Sign the outbound callback so the receiver can verify it came from you — HMAC-SHA256 over the body with a per-account secret, in an X-DataPilot-Signature header.
  • Set X-Client-Channel: webhook so it lands in query_runs.channel. No migration needed — the column is free-text by design.
Done when: curl with a key returns 202 and the answer arrives at a local callback receiver, with the run visible in /ops tagged channel='webhook'.
rung 2

Slack

~1 day

A slash command returns a governed answer from the bot's own data scope, with the asking human recorded in the audit trail.

  • Slack authenticates differently. It will never send your bearer key — it signs its own requests. Verify X-Slack-Signature as v0=HMAC_SHA256("v0:{timestamp}:{raw_body}", signing_secret), and reject any request whose timestamp is more than 5 minutes old (replay window). The bot's dpk_ key is then used internally to resolve identity — Slack's signature proves the request is genuine, the service account decides what it can see. Two separate jobs; don't collapse them.
  • Read the RAW body before FastAPI parses it — await request.body(). Signature verification over a re-serialised dict will fail intermittently and cost you an afternoon.
  • The 3-second ack. Return 200 immediately with an ephemeral "Working on it…", then a background task POSTs the real answer to response_url. This is not optional — Slack times out and shows the user an error otherwise.
  • Audit the human. Persist Slack's user_id, user_name and channel_id into the query_runs trace / an app.events row. They don't affect RLS — that's the trade you've chosen — but "who asked" must still be answerable.
  • Ship the plain-text answer field. Rendering the rich pages objects as Slack blocks or a PNG is genuinely new work — nothing outside React/visx renders them today.
  • Slack signing secret goes in Secrets Manager, plumbed like logfire-token.
Done when: a slash command in a real workspace returns a property answer inside 3 seconds of ack, the full answer lands in-channel, and /ops shows the run tagged channel='slack' with the asking Slack user recorded.
rung 3

MCP server

~1–2 days

Yes — this is a real, standalone MCP server, and to answer your question directly: rung 3 is what closes "tell me about an MCP server you built."

new service — services/mcp-server/ · its own Dockerfile, its own pyproject.toml, a compose entry, and its own App Runner service in apprunner.tf. Follows the shape of the existing three services.

Built with FastMCP over streamable HTTP (the remote transport; stdio is for local-only servers). It does not talk to Postgres directly — it calls backend-api's HTTP surface with its own dpk_ service key, so guardrails, RLS, limits and the audit trail all stay in one place and can't drift between two codebases. Tools, per your s06:

  • list_datasets — what this key can see
  • describe_schema — tables and columns for one dataset
  • ask_question — natural language → governed answer
  • run_governed_query — SQL → the existing sql_guardrails path
  • get_audit — recent runs for this key

Tool-surface design is the senior signal, more than the plumbing: tight JSON schemas, the right granularity (not one god-tool, not fifteen noisy ones), and descriptions written so the model picks correctly. Budget real time for the descriptions — that's the part people skip and the part that determines whether it works.

Choosing a separate service costs you one thing — the key-verification helper now lives in two places, or gets duplicated. Keep it thin and copy it rather than inventing a shared package for ~30 lines; premature extraction across service boundaries is its own trap in a repo this size.
Be honest about what this does and doesn't clear. Bearer-key auth does not meet your own s05 bar #3 ("OAuth 2.1, scoped tokens, a separate token for the upstream API"). Shipping v1 on service keys is a reasonable stage — but write the gap down in the README rather than letting it read as complete. "Here's why I didn't need MCP for X" and "here's the auth tier I stopped at and why" are both senior answers; silence isn't.

Proving it works — two tiers, because one isn't enough

You asked for a test that spins up Claude against the MCP server and answers a question. That's the right acceptance test, but it can't be the only one: it needs an API key, costs tokens, and is non-deterministic, so it can't gate every PR. Split it.

Tier 1 — protocol conformance. services/mcp-server/tests/test_mcp_protocol.py · deterministic, no LLM, runs in CI

  • Connect with the mcp Python client over streamable HTTP.
  • list_tools() returns exactly the five tools, with the expected input schemas — this catches a renamed or malformed tool before a model ever sees it.
  • call_tool("ask_question", …) returns a governed answer.
  • A dataset the key isn't granted returns empty, not an error that leaks its existence.
  • A revoked key fails the connection.

Tier 2 — real client, end to end. make mcp-smoke · live only, self-skips without ANTHROPIC_API_KEY — the same pattern the journey evals already use

  • Launch Claude configured with the deployed MCP server, ask a real property question ("what was the average weekly rent in postcode 2077 last quarter?"), and assert on the result.
  • Assert the model actually called your tool. Inspect the message stream for an mcp__datapilot__* tool-use block before you assert anything about the answer text.
  • Then assert the returned figure matches a direct SQL query against the same marts — so the test proves the data path, not just that a response arrived.

The trap: this test passes when the server is completely broken

Claude knows roughly what Sydney rents cost. Ask it about postcode 2077 with a dead MCP server and it will happily produce a plausible dollar figure from parametric memory — and a test that only checks "$" in answer goes green. The tool-use assertion is the actual test; the answer check is secondary. Verify it by pointing the test at a deliberately misconfigured server once and confirming it fails.

Implementation note for whoever builds this: the Claude Agent SDK and the claude CLI both support MCP servers, but their config bindings differ and change. Read the current Agent SDK docs for the exact option shape rather than guessing it — or take the lower-risk route and drive the documented claude CLI headless with an --mcp-config file and a -p prompt, parsing its JSON output for the tool-use block.

Done when: tier 1 is green in CI, make mcp-smoke passes against the deployed server, and the README carries the client config snippet. That snippet plus a recording of the smoke test is the portfolio artifact — it's the thing you open when someone asks "tell me about an MCP server you built."
rung 4

Key management — endpoints and a Settings tab

~0.5–1 day

Mint, list and revoke keys without touching SQL.

services/backend-api/app/routers/service_accounts.py — all behind Depends(require_admin), the repo's established admin pattern · frontend/src/features/settings/ — a panel in the existing Settings tab

  • POST /admin/service-accounts — create; returns the full key once, in the response body only
  • GET /admin/service-accounts — list: name, surface, key_id, last_used_at, revoked state. Never the hash.
  • POST /admin/service-accounts/{id}/revoke — set revoked_at

The UI must make "shown once" unmistakable

Display the key in a copy-to-clipboard block with an explicit warning that it will never be shown again, and no way to re-reveal it. If the UI implies it can be recovered later, someone will not copy it, and you'll be debugging that instead of building.

Done when: an admin can mint a Slack key in the UI, use it, revoke it, and watch the next call 401.

Non-negotiable — carry these into every rung

The raw key exists exactly once

Returned by the mint endpoint, never stored, never logged, never in a URL or query string. Only key_id is safe to log. If someone loses it, they rotate — there is no recovery path, and that's the correct design.

Grant each key the narrowest dataset set that works

With channel membership as the access boundary, the bot's dataset_access rows are the security policy. Never grant a service account "everything because it's easier" — that converts a deliberate trade-off into an actual hole.

No identity may arrive from the caller

There is no act-as in v1, so no request field or header may influence which app.users row is used. If a future delegation feature adds one, it must be allowlist-checked and default-deny — never a fallback to a broader identity on lookup miss.

Identity is resolved in backend-api, before the agent hop

data-agent trusts the user.id in the request body (it sits behind the shared X-Agent-Token). That trust is only sound because backend-api derives the id from a verified credential. Never let a caller-supplied user id reach ask_agent().

Never rls_connection(None) on a service request

An empty RLS context makes every protected table return zero rows — silently, with no error. Always pass the resolved user.id.

A service account is never an admin

role stays 'user'. Tier usage limits via the new plan='service' instead. A leaked key must not be able to read across users.

Revocation is checked per request

revoked_at IS NULL on every call, no caching in v1. Revocation that takes effect in five minutes is not revocation.

Risks

A new auth path in production

Today prod routes every bearer through Google verification. This adds a branch that bypasses it. Mitigation: the branch triggers only on the dpk_ prefix, is checked before auth_mode, and applies the same strictness in every environment — it must not become a dev-mode backdoor that happens to be reachable in prod.

A leaked key is a standing read grant

Mitigations in v1: per-account grants kept minimal, immediate revocation, last_used_at for detection, and surface pinning so a Slack key can't drive the MCP endpoint. Short-lived tokens and scope enforcement are the natural rung-4.

Slack's 3-second ack

The single most common way this build fails in front of someone. Ack first, answer later, always — and test it against a real workspace, not a mock.

Follow-up questions won't work

Conversation memory is absent (P2). In Slack this bites harder than in the UI, because a thread looks like a conversation. Either ship P2 first or say plainly in the bot's help text that each question stands alone.

Four rungs in one branch is a big review surface

You chose one branch, which is fine — but the auth branch is the security-critical part and shouldn't be skimmed because it's commit 1 of 40. Mitigation: one commit per rung, so the PR reads rung-by-rung even as a single branch, and a /no-mistakes pass before the adapters land on top of the auth.

Rollback: every rung is additive — one new table, new routers, one auth branch, one new service. Reverting an adapter is dropping its router registration; the auth branch is inert without a dpk_ token. Migration 0032 needs a mirrored downgrade() per house style.

Documented upgrade path — delegation, when you need it

Not being built now. Written down so the decision is legible later, and so the v1 boundary reads as a choice rather than a limit.

The trigger: the first time someone asks for a Slack surface over data where two people in the same channel should see different answers. The shape: a migration adding app.service_account_subjects (account_id, subject, user_id) plus an allow_act_as flag; an X-Act-As-Subject header resolved against that table with default-deny on a miss; and a /link slash command so a Slack user can bind their own account. The mapping table is the allowlist — there is no open impersonation path at any point. Roughly a day on top of what's built here, because rung 0 already does the hard part.
