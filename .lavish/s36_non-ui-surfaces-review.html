Four front doors. One brain.

What the s35 work actually built, how to test every piece of it, how it is hosted — and a straight answer to “can I have one data-agent service that serves both the app and webhooks?”

the short answer

You already have exactly that. There is one pipeline — run_question() in backend-api — and the browser, the webhook, Slack and MCP all enter through it. The MCP server is not a second agent; it is a ~200-line protocol adapter with no database credentials that calls that same pipeline over HTTP. The only genuinely open question is whether that adapter keeps its own container.

01Your four questions, answered first

Each of these is checked against the code on the branch, not against the plan.

Q1

“I believe you’ve made an MCP server for the data-agent.”

Yes — but it never touches data-agent.

It exposes the data-agent’s capability (ask a question, run governed SQL, list datasets, describe schema, read the audit trail) while talking only to backend-api over HTTP.

That is the deliberate bit: services/mcp-server/mcp_server/config.py holds no DATABASE_URL at all. Its only capability is a dpk_ key. So the SQL guardrails, RLS scoping, daily cap and audit write exist in one implementation and cannot drift.

Q2

“Can that MCP server be used to answer questions in the app, or in another surface via a webhook?”

No — and it shouldn’t be.

MCP is inbound only. It is a door into Data Pilot for external MCP clients (Claude Code, Claude Desktop, another agent). Nothing inside the product consumes it.

The app already calls run_question() directly, in-process. Routing the UI through MCP would add a network hop, a serialisation round trip and a second auth identity to reach code it can already call. The webhook is a sibling front door on backend-api, not something layered on top of MCP.

Q3

“How is the server hosted — docker?”

Docker locally, App Runner in AWS.

Local: services/mcp-server/Dockerfile → compose service mcp-server on port 8200, already running in your stack.

AWS: aws_apprunner_service.mcp_server in infra/terraform/foundations/apprunner.tf, image pushed by scripts/aws_build_push.sh (now five images, not four), key injected from Secrets Manager. Not deployed yet — it lands on the next merge to main.

Q4

“I want one data-agent service that serves webhooks and the app.”

Built. One pipeline, four doors.

routers/ask.py :: run_question() is the single implementation of cap → agent → persist → respond. /ask, the webhook, Slack and MCP all call it. data-agent itself was not modified at all by s35 — check the diffstat.

What is still a choice: the MCP adapter is currently its own container. It could be mounted into backend-api instead. That comparison is below.

The one thing MCP could plausibly do for the app later

MCP’s real leverage is the other direction: letting data-agent become an MCP client and pull in outside tools — an ABS statistics server, a geocoder, a docs server — so the agent can reach data it doesn’t own. That is a genuinely different piece of work and nothing in s35 blocks or presumes it.

05The topology decision — the only thing still open

You asked for “ideally one data-agent service that serves webhooks and the app”. You have it. The remaining choice is narrower than it looks: does the MCP protocol adapter run as its own process, or inside backend-api?

A · Separate adapter container

shippedrecommended

mcp-server is its own image, its own compose service, its own App Runner service. It speaks MCP outward and plain HTTP inward.

  • Clean trust boundary — the process that terminates an unauthenticated public protocol holds zero DB credentials.
  • Independent blast radius: a bad MCP transport release cannot take the UI’s API down.
  • Scales and deploys separately; can move to a different host entirely.
  • The MCP SDK’s DNS-rebinding TransportSecuritySettings stay isolated from the app’s CORS and session middleware.
  • One more container. In AWS that is one more App Runner instance to pay for and watch.
  • An extra network hop per tool call (localhost in compose, VPC-internal in AWS).

B · Mount MCP inside backend-api

feasible — verified

Delete the container; mount the MCP ASGI app on backend-api at /mcp. One service, one deploy, one bill.

  • One fewer container, image, App Runner service and alarm.
  • No internal hop; no second dpk_ key to mint and rotate — it could resolve identity in-process.
  • Real wiring cost. MCPServer.streamable_http_app() returns a Starlette app with its own lifespan that starts the MCP session manager. FastAPI’s Mount does not run a mounted app’s lifespan, so backend-api’s lifespan has to drive it explicitly. Get it wrong and MCP fails at runtime, not at boot.
  • Couples an evolving beta protocol’s transport security to your product API.
  • Loses the “no DB credentials” property — the MCP surface would run in the process that holds them.

C · Put MCP inside data-agent

rejected

“One data-agent service that serves everything”, read literally.

  • data-agent holds agent_ro and admin_ro database credentials and runs model-authored SQL. It is the last process that should terminate a public protocol.
  • It implements no auth, no daily cap, no audit write, no conversation persistence — all of that is backend-api’s. You would be rebuilding the security surface in a second place.
  • Four front doors would become two security surfaces. That is the exact failure the s35 design exists to prevent.
Recommendation: keep A, and don’t conflate “one agent” with “one process”

“One data-agent service” is already true in the sense that matters — there is a single implementation of the ask pipeline, a single security surface, and a single audit trail. The MCP container is an adapter, the same way a load balancer or a TLS terminator is: it adds a protocol, not a brain.

Option B is a legitimate cost optimisation and it is genuinely feasible (I checked the SDK — streamable_http_app() exists and returns a Starlette app). Take it only if the extra App Runner instance is the thing you want to cut. It buys ~$15–25/month and costs you the isolation property.

local · docker compose

Already running in your stack

Built from services/mcp-server/Dockerfile (uv on python3.12-bookworm-slim), published on :8200, endpoint http://localhost:8200/mcp. depends_on: backend-api.

aws · app runner

Defined, not yet deployed

aws_apprunner_service.mcp_server — ECR image data-qa/mcp-server, port 8200, key from Secrets Manager (data-qa/mcp-service-key), no instance IAM role because it talks to nothing but backend-api.

The image is now part of scripts/aws_build_push.sh, which the deploy workflow runs — so it ships automatically on the next merge to main.

Deployment gotcha you will hit exactly once: ALLOWED_HOSTS needs two applies

The MCP SDK ships DNS-rebinding protection that matches the Host header including the port. There is no allow-everything value, and the wildcard form is host:* — a bare * never matches. App Runner only assigns the hostname at create time and a service cannot reference its own service_url, so the value cannot be derived in Terraform.

Result: after the first apply, every remote MCP request returns 421 until you set var.mcp_allowed_hosts from the mcp_allowed_hosts_hint output and apply again. Both outputs exist to make this a two-step you can see rather than a mystery.

Why the ordering is the whole design

Claude knows roughly what Sydney property costs. Point it at a dead MCP server and it will happily produce a plausible-looking number from memory — so a test that only looked for a figure in the output would go green while the server was completely broken.

mcp_smoke.py therefore parses the streamed events and fails unless it sees an actual mcp__datapilot__* tool_use block, and only then checks the number. I verified both branches: server down → exit 1 with “answered WITHOUT calling any MCP tool”; server up → exit 0.

TIER 3

Slack — locally by hand, then for real

~15 min

Locally, without a workspace. Mint a key with surface slack first — the endpoint returns 503 until one exists, since it looks the identity up by surface and never takes it from the request. Then sign a request the way Slack would:

hand-signed slash command
SECRET=dev-slack-secret          # the compose default
TS=$(date +%s)
BODY='text=median+rent+in+2077&response_url=https%3A%2F%2Fwebhook.site%2Fyour-uuid&user_id=U01&user_name=nathan&channel_id=C01'
SIG="v0=$(printf 'v0:%s:%s' "$TS" "$BODY" \
  | openssl dgst -sha256 -hmac "$SECRET" -r | cut -d' ' -f1)"

curl -sS -X POST http://localhost:8000/integrations/slack/command \
  -H "X-Slack-Request-Timestamp: $TS" \
  -H "X-Slack-Signature: $SIG" \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data "$BODY"

# → {"response_type":"ephemeral","text":"Working on it — median rent in 2077"}
# → the real answer POSTs to the response_url a minute later

Tamper with one character of $BODY after signing, or set TS ten minutes in the past, and both must return 401.

For real. Slack needs a public HTTPS URL, so this is a post-deploy step:

Understand the Slack access model before you invite anyone

v1 answers as one bot identity with its own dataset grants. Channel membership is the access boundary. Everyone in that channel sees the same scope, so grant a Slack account only what the whole channel should see. Per-user delegation is designed and documented in AGENTS.md, and deliberately unbuilt.

Authorisation is shared; accountability is not — the asking user’s id, name and channel are written to app.events against every run.

08Review of the approach

What I think holds up, and what I would flag to a reviewer before this goes anywhere public. The gaps are stated as gaps, not as future work I’m confident you’ll never need.

What holds up

strong

One pipeline, not four

Every door funnels into run_question(). Four adapters that each reimplemented the cap and the audit write would be four chances to get it wrong, and they would drift. This is the single best property of the design.

strong

A machine that is still a user

Because a service account is an app.users row, RLS, grants, conversations and query_runs all work with no special-casing. No “machine bypass” path was added, which is where this normally goes wrong.

strong

Never admin

Machine callers are tiered with plan='service', not exempted by role. A leaked key cannot read across users. app.service_accounts is granted to app_user only — never agent_ro, which runs model-authored SQL. I verified that grant rather than assuming it.

strong

Hash, not KDF — on purpose

SHA-256 rather than bcrypt/argon2 is correct here: the secret is 256 bits of CSPRNG output, so there is no dictionary to attack, and a KDF would only add latency to every request. Compared with secrets.compare_digest.

strong

Tests that can actually fail

The MCP smoke test asserts tool_use before figures, and the /sql wrapper raises on the 200-with-error-field contract — a real bug I hit, where a blocked DELETE reached the model as an empty success.

strong

Unconfigured means closed

No SLACK_SIGNING_SECRET → the endpoint 404s rather than existing in a weakened form. No MCP_SERVICE_KEY → tools say so plainly instead of half-working.

Gaps — honest list

MCP auth is a static bearer key
mcp_server/config.py		 blocks public use The MCP spec’s auth story is OAuth 2.1 with scopes and dynamic client registration. A shared key does not meet that bar. Fine for a private deployment where you control every client; not fine for anything published. OAuth 2.1 resource server, or keep it behind a private network. Already written down in AGENTS.md as a deliberate, staged gap.
run_governed_query has no daily cap
routers/sql.py:47		 cost / abuse check_daily_llm_cap guards /ask and /sql/ai but not raw POST /sql. So an MCP client can run unlimited governed SELECTs. It is not a data leak — SELECT-only, allowlisted, RLS-scoped, 15s statement timeout, audited — but it is an unbounded query rate. Either extend the cap to /sql for plan='service', or add a per-key rate limit. Small change; worth doing before prod exposure.
Callbacks signed with the agent shared token
integrations.py:104		 shortcut We only store a hash of the caller’s secret, so it cannot be used to sign. The agent shared token is the one secret both ends can hold — so every webhook caller’s callbacks are signed with the same key.
