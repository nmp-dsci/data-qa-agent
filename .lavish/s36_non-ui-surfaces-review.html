01Your four questions, answered first

Each of these is checked against the code on the branch, not against the plan.

Q1

“I believe you’ve made an MCP server for the data-agent.”

Yes — but it never touches data-agent.

It exposes the data-agent’s capability (ask a question, run governed SQL, list datasets, describe schema, read the audit trail) while talking only to backend-api over HTTP.

That is the deliberate bit: services/mcp-server/mcp_server/config.py holds no DATABASE_URL at all. Its only capability is a dpk_ key. So the SQL guardrails, RLS scoping, daily cap and audit write exist in one implementation and cannot drift.

Q2

“Can that MCP server be used to answer questions in the app, or in another surface via a webhook?”

No — and it shouldn’t be.

MCP is inbound only. It is a door into Data Pilot for external MCP clients (Claude Code, Claude Desktop, another agent). Nothing inside the product consumes it.

The app already calls run_question() directly, in-process. Routing the UI through MCP would add a network hop, a serialisation round trip and a second auth identity to reach code it can already call. The webhook is a sibling front door on backend-api, not something layered on top of MCP.

Q3

“How is the server hosted — docker?”

It no longer needs its own hosting at all.

Docker locally on :8200, App Runner in AWS. That was true when you asked. After your option B decision the surface is mounted on backend-api, so it is hosted wherever backend-api already is — compose locally, App Runner in AWS.

Deleted outright: services/mcp-server/, its Dockerfile and image, the compose service, aws_apprunner_service.mcp_server, the ECR repo (back to four images) and the data-qa/mcp-service-key secret.

Q4

“I want one data-agent service that serves webhooks and the app.”

Built. One pipeline, four doors.

routers/ask.py :: run_question() is the single implementation of cap → agent → persist → respond. /ask, the webhook, Slack and MCP all call it. data-agent itself was not modified at all by s35 or s36.

Resolved. You picked option B, so the last separate piece is gone too: the MCP tools now call those handlers in process. Four front doors, one pipeline, one deployable API. The comparison, and what it actually cost, is below.

05The topology decision — resolved

You asked for “ideally one data-agent service that serves webhooks and the app”. The choice was narrower than it looked: does the MCP protocol adapter run as its own process, or inside backend-api? You picked B. Both cards are kept as the record of the trade that was made.

A · Separate adapter container

was shipped in s35superseded

mcp-server is its own image, its own compose service, its own App Runner service. It speaks MCP outward and plain HTTP inward.

  • Clean trust boundary — the process that terminates an unauthenticated public protocol holds zero DB credentials.
  • Independent blast radius: a bad MCP transport release cannot take the UI’s API down.
  • Scales and deploys separately; can move to a different host entirely.
  • The MCP SDK’s DNS-rebinding TransportSecuritySettings stay isolated from the app’s CORS and session middleware.
  • One more container. In AWS that is one more App Runner instance to pay for and watch.
  • An extra network hop per tool call (localhost in compose, VPC-internal in AWS).

B · Mount MCP inside backend-api

your choiceshipped · verified live

The container is deleted; the MCP ASGI app is mounted on backend-api at /mcp. One service, one deploy, one bill.

  • One fewer container, image, App Runner service, ECR repo and secret.
  • No internal hop, and no server-side key at all — identity now resolves per request from the client’s key.
  • Unplanned win: auth got stronger. The old container accepted any client that could reach :8200 and used its key only for the hop inward. Now the client must present a dpk_ key pinned to surface='mcp', checked in raw ASGI ahead of the JSON-RPC transport — an anonymous caller cannot even open a session.
  • Unplanned win: the two-apply deploy trap is gone. With a key gate in front, the DNS-rebinding allowlist is defence-in-depth rather than the control, so it is off unless configured — no more “every remote request 421s until a second apply”.
  • The wiring cost was real, exactly as flagged. streamable_http_app() creates the session manager lazily and Starlette does not run a mounted app’s lifespan — mounting alone gives a surface that imports fine, boots fine, then dies on the first tool call. backend-api’s lifespan drives it explicitly.
  • Isolation is genuinely lost. The MCP surface now runs in the process holding the database credentials. Nothing in it touches the DB directly, but the property is gone and is written down as gone.
  • A wart that had to be fixed: Starlette compiles Mount("/mcp") to ^/mcp/(.*)$, so a bare /mcp 307-redirected. A path normalizer makes the obvious URL the working one.

C · Put MCP inside data-agent

rejected

“One data-agent service that serves everything”, read literally.

  • data-agent holds agent_ro and admin_ro database credentials and runs model-authored SQL. It is the last process that should terminate a public protocol.
  • It implements no auth, no daily cap, no audit write, no conversation persistence — all of that is backend-api’s. You would be rebuilding the security surface in a second place.
  • Four front doors would become two security surfaces. That is the exact failure the s35 design exists to prevent.
Outcome — I recommended A, you chose B, and B turned out better than I priced it

My case for A rested on the isolation property. That cost is real and was paid: the MCP surface now runs in the process holding the database credentials.

What I under-weighted is that folding it in forced a client-auth gate. As a separate service, MCP had no client authentication at all — anyone who could reach :8200 got the full grants of the mcp service account. Mounting it on the public API made that untenable, so the key moved to the client. The surface ends up more locked down than the design I recommended, not less, and a whole class of deploy failure (the 421 two-apply dance) disappeared with it.

Verified end to end rather than assumed: a real Claude CLI session called list_datasets then ask_question through the mount and returned the ground-truth 15,217; anonymous gets 401; a webhook-surface key gets 403; a blocked DELETE still surfaces as a tool error rather than an empty success.

06Hosting — local and AWS

local · docker compose

Nothing of its own to run

The surface is part of backend-api, so make up is all there is. Endpoint: http://localhost:8000/mcp.

No BACKEND_URL, no server-side MCP_SERVICE_KEY — the client brings the key. The one optional knob is MCP_ALLOWED_HOSTS, unset by default.

aws · app runner

Ships with backend-api

No dedicated service. aws_apprunner_service.mcp_server, the data-qa/mcp-server ECR repo and the data-qa/mcp-service-key secret are all deleted; aws_build_push.sh is back to four images.

Endpoint after deploy: https://<backend-api>/mcp. Mint a key for surface='mcp' and hand it to whoever runs the client.

The ALLOWED_HOSTS two-apply trap is gone — and it is worth knowing why

The MCP SDK’s DNS-rebinding protection matches the Host header including the port, with no allow-everything value. App Runner assigns a hostname at create time and a service cannot reference its own service_url, so the allowlist could not be derived in Terraform — every remote request returned 421 until a second apply.

Rebinding protection exists to defend unauthenticated servers reachable from a browser. Now that a dpk_ key is required in front of the transport, there is no anonymous path for such an attack to reach, so the allowlist is defence-in-depth and defaults to off. The deploy works first time.

You have a generic front door. The question is what to plug into it — and where to test it before anything real is on the other end. Ranked for this product: a governed property-data agent, built as a portfolio piece.

Zapier, Make or n8n each speak “generic HTTP webhook” natively and each fans out to thousands of downstream apps. Where to test — and the direction that trips people up

There are two flows here and they need different tools. Your webhook is both a server and a client: something calls you, then you call them back.

direction 1 · inbound

Something calls your webhook

Locally this needs no tooling at all — curl or Postman against localhost:8000 is the whole test, and it is what tier 1 above does.

It only gets interesting when a real SaaS must reach you, because Slack and Zapier cannot see your laptop. Two options:

  • ngrok or Cloudflare Tunnel — a public HTTPS URL pointed at localhost. Best while iterating, since you keep your debugger.
  • Just deploy. Once PR #30 merges you have a real App Runner HTTPS URL and need no tunnel at all. For Slack this is the simpler path.
direction 2 · outbound

You call their callback_url

This is the half people forget, and it is where your signed delivery needs proving. You need a URL that catches a POST and shows you exactly what arrived.

  • webhook.site — instant URL, zero signup, shows headers and body. Best for confirming X-DataPilot-Signature is actually present.
  • Pipedream RequestBin — same, plus you can run JS on the payload, so you can verify the HMAC right there.
  • Beeceptor — adds mock responses, useful for testing how you behave when a callback returns 500.
  • Hookdeck — production-grade: retries, replay, delivery history. Worth knowing about; overkill today.
The failure case worth testing deliberately

Point callback_url at a URL that returns 500, or at a dead host, and confirm the run still lands in query_runs. It should: delivery failure is logged and swallowed on purpose, because the answer is already persisted and a dead callback is the caller's problem to notice — not a reason to lose the run. That is a design decision worth being able to demonstrate rather than just assert.

There is no retry queue. If you want one, Hookdeck in front of your callbacks is the buy-not-build answer.

09Review of the approach

What I think holds up, and what I would flag to a reviewer before this goes anywhere public. The gaps are stated as gaps, not as future work I’m confident you’ll never need.

What holds up

strong

One pipeline, not four

Every door funnels into run_question(). Four adapters that each reimplemented the cap and the audit write would be four chances to get it wrong, and they would drift. This is the single best property of the design.

strong

A machine that is still a user

Because a service account is an app.users row, RLS, grants, conversations and query_runs all work with no special-casing. No “machine bypass” path was added, which is where this normally goes wrong.

strong

Never admin

Machine callers are tiered with plan='service', not exempted by role. A leaked key cannot read across users. app.service_accounts is granted to app_user only — never agent_ro, which runs model-authored SQL. I verified that grant rather than assuming it.

strong

Hash, not KDF — on purpose

SHA-256 rather than bcrypt/argon2 is correct here: the secret is 256 bits of CSPRNG output, so there is no dictionary to attack, and a KDF would only add latency to every request. Compared with secrets.compare_digest.

The MCP smoke test asserts tool_use before figures, and the /sql wrapper raises on the 200-with-error-field contract — a real bug I hit, where a blocked DELETE reached the model as an empty success.
