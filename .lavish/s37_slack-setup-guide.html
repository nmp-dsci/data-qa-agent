Data Pilot in Slack — prod setup & test guide

Goal: type /datapilot median rent in 2077 in your data-pilot workspace and get a governed answer back in the channel — served by the production backend on AWS, the same pipeline as prod web chat.

Verdict

Yes — loop it in and it answers, straight off prod. The Slack surface is already deployed: POST /integrations/slack/command on the App Runner backend verifies Slack's signature, acks inside 3 seconds, runs the question through the exact /ask pipeline (caps, RLS, audit), and posts the answer back to the channel. s35 even pre-provisioned the AWS secret for the signing key — it sits at a placeholder that keeps the endpoint closed until you fill it. 4 steps, ~15 minutes, zero code, zero Terraform. One shape note: v1 is a slash command, not an @mention bot — it doesn't read messages, you invoke it.

01How it answers

Two separate jobs that make the design safe: Slack's signature proves the request is genuinely from your workspace, and a single service account decides what may be seen. Nothing in the request can change which identity answers.

The ack and the answer are decoupled — a 90-second agent run never fights Slack's 3-second timeout. Code: services/backend-api/app/routers/integrations.py

Identity

One bot, its own grants

The earliest active service account with surface = 'slack' answers every question. Channel membership is the access boundary — grant that account only the datasets everyone in the channel should see.

Accountability

The asker is still recorded

Authorisation is the bot's; accountability is the human's. Every question writes a slack_question event with the Slack user, name, channel and run_id — "who asked this" stays answerable.

No bearer key in Slack

Signature, not secret-sharing

Slack can't hold a dpk_ key safely, so it doesn't get one. It signs its own requests; the backend verifies the HMAC over the raw body against the app's signing secret. Placeholder secret = the endpoint 404s out of existence.

02The setup — 4 steps, all prod

Verified against the deployed stack: the backend URL below is the live App Runner service, the Secrets Manager secret data-qa/slack-signing-secret already exists (Terraform created it with a REPLACE_ME_VIA_CLI placeholder), and App Runner already injects it as SLACK_SIGNING_SECRET. Nothing to deploy.

Mint the Slack service account — in prod prod app → Settings

Open deqfc8b0u8s64.cloudfront.net and sign in with Google (your admin email) → Settings → Service accounts:

  • Name it slack-bot, keep surface = slack (the default)
  • Tick the datasets the whole channel may see — an account with zero grants mints fine but answers nothing (the form warns you)
  • Press Mint key
You can ignore the dpk_ key it shows. Slack never sends it — the signature authenticates requests. What matters is that an active account with surface = slack exists in the prod database. A local mint doesn't count: prod has its own DB. No account = the channel gets a 503 "No active Slack service account is configured".

Create the Slack app + slash command api.slack.com/apps

  • Go to api.slack.com/apps → Create New App → From scratch
  • Name: Data Pilot · Workspace: data-pilot
  • In the app's sidebar: Slash Commands → Create New Command
    • Command: /datapilot
    • Request URL: https://hzxtrasvdp.ap-southeast-2.awsapprunner.com/integrations/slack/command
    • Short description: Ask the governed property data a question
    • Usage hint: median rent in 2077
    • Leave "Escape channels, users…" unticked → Save
Seeing "Socket Mode is enabled. You won't need to specify a Request URL"? Turn it off first: app sidebar → Settings → Socket Mode → toggle Enable Socket Mode off. Socket Mode is Slack's WebSocket transport for apps with no public endpoint — with it on, Slack never calls a URL, so it would never reach the backend. Data Pilot has a public endpoint and authenticates via the signing secret, so it uses the Request URL path. Once Socket Mode is off, the Request URL field appears on the slash command form — paste the URL above.
That Request URL is the live prod backend (App Runner URLs are stable across deploys). If it ever looks wrong, the source of truth is terraform output backend_api_url in infra/terraform/foundations.

Fill the signing secret in AWS + roll the backend terminal

App page → Settings → Basic Information → App Credentials → Signing Secret (press Show, copy). Then:

# 1. refresh credentials — your data-qa profile is AWS SSO; this opens the browser,
#    approve the sign-in there, then the terminal continues on its own
aws sso login --profile data-qa
aws sts get-caller-identity --profile data-qa   # sanity check: Account = 089783391188

# 2. put the signing secret into the pre-provisioned slot.
#    The value comes FROM SLACK: api.slack.com/apps → your "Data Pilot" app →
#    Settings → Basic Information → App Credentials → "Signing Secret" → Show → copy.
#    (Not the Client Secret sitting next to it — see the warning below.)
aws secretsmanager put-secret-value \
  --secret-id data-qa/slack-signing-secret \
  --secret-string '<the Signing Secret you copied from Slack>' \
  --profile data-qa --region ap-southeast-2

# 3. App Runner resolves secrets at deploy time — roll the backend to pick it up:
ARN=$(aws apprunner list-services --profile data-qa --region ap-southeast-2 \
  --query "ServiceSummaryList[?contains(ServiceName,'backend')].ServiceArn" --output text)
aws apprunner start-deployment --service-arn "$ARN" --profile data-qa --region ap-southeast-2
Classic mistake: copying the Client Secret instead of the Signing Secret. They sit near each other on the same page; only the Signing Secret verifies X-Slack-Signature. Wrong one = every command 401s — and after correcting it you must roll the deployment again.

Install the app to the workspace api.slack.com/apps

App page → Settings → Install App → Install to data-pilot → Allow. Creating the slash command already granted the only scope it needs (commands). Slash commands work in every channel and DM once installed — no need to invite a bot user for v1.

Prove the governance trail

Every Slack answer is a first-class prod run. In the prod app's SQL editor (as admin):

-- the runs Slack produced
SELECT id, created_at FROM app.query_runs WHERE channel = 'slack' ORDER BY created_at DESC LIMIT 5;

-- who asked each one (Slack user, name, channel, run_id)
SELECT payload FROM app.events WHERE event_type = 'slack_question';

The Flight Deck (/ops in the prod app) shows the runs land in the activity telemetry too.

04When it doesn't work

Each symptom has exactly one usual cause. Work top to bottom.

Symptom (in Slack)MeaningFix
dispatch_failed / "command failed" Slack couldn't reach the Request URL inside 3s Check the Request URL matches the backend exactly (path /integrations/slack/command); curl it — anything but 401 means the backend side isn't ready
Slash command form has no Request URL field ("Socket Mode is enabled…") Socket Mode is on — Slack expects a WebSocket client instead of calling a URL, so the backend would never be reached App sidebar → Settings → Socket Mode → toggle off, then edit the slash command and paste the Request URL
Nothing at all, curl says 404 Endpoint deliberately closed: secret still at placeholder, the deployment wasn't rolled after setting it — or the roll is still in progress (a deployment takes ~4–5 min; old instances keep serving 404 until it finishes) put-secret-value then start-deployment (step 03), then wait for the operation to report SUCCEEDED before re-checking
Every command errors, logs show 401 Bad Slack signature Wrong secret — usually the Client Secret was copied Re-copy Signing Secret from Basic Information, re-run step 03 including the deployment roll
Ack arrives, then "Couldn't answer that: No active Slack service account…" Step 01 missed, done on local instead of prod, or the account was revoked Mint a service account with surface = slack in the prod app's Settings
First question after a quiet spell is slow or fails once Aurora auto-paused (1h idle) and takes ~15s to resume; the ack still lands because the signature check touches no database Ask again — the second run answers. Same cold-start behaviour as prod login (s29)
Ack arrives, answer never does The background run failed after the ack CloudWatch logs for the backend App Runner service — look for slack question failed / response_url delivery failed; the run row in query_runs still tells the story
Answers are empty-ish / "no data" The bot account has no (or the wrong) dataset grants Re-mint in prod with the datasets ticked — grants are set at mint time
"Couldn't answer that: …daily limit…" Service-account cap hit (200 questions/UTC day) It resets at midnight UTC — the cap is the leaked-key blast-radius bound, leave it in place for prod

05Known edges of v1

By design

Text only, one message

Slack gets the answer sentence (capped at 3,000 chars) — no charts, no report pages. The full report exists in the app; richer Block Kit answers are the decision below.

By design

Invoked, not listening

A slash command only fires when typed. Data Pilot doesn't read the channel and won't respond to @Data Pilot mentions — that's the Events API, also in the decision below.

Prod reality

Cold starts & real spend

Aurora auto-pauses after 1h idle — the first answer after a quiet spell can be slow or fail once (~15s resume; ask again). And every question is real LLM spend on the prod key, bounded by the 200/day cap.
