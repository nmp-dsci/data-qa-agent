Demo-mode prod: a zero-login, zero-LLM showcase

Turn the AWS deployment into a walk-in portfolio demo: an employer clicks a link and lands straight in the app — no login, no cold pitch. The agent's answers are recorded in dev and replayed in prod, so the chat feels alive but never touches an LLM. Explore and the SQL editor stay genuinely live (they never needed an LLM). Capped for 10–20 concurrent visitors with a bounded worst-case bill under attack. Then the same pattern rolls out to every other portfolio app.

Verdict — is it cheaper?

Yes, roughly 60–70% cheaper (~US$36–66/mo → ~$8–18/mo), but not mainly because of the LLM. DeepSeek was already cheap and daily-capped (~$1–5/mo). The real savings: demo mode lets you delete the data-agent App Runner service (2 vCPU / 4 GB — the single biggest idle line at ~$25–35/mo) and drop its secrets. The bigger win is risk, not dollars: a no-login app with a live LLM has an unbounded abuse bill; a cached demo's worst case is a fixed, capped ceiling. No login + live LLM was never a safe combination — caching is what makes "no login" possible at all.

08Risks & failure modes

Replay drift

Stored pages vs an evolving report engine. Mitigation: the s20 object-parity CI gate already fails on unrenderable stored objects; add the demo pack to that gate's fixtures. Re-recording is one dev session whenever the product changes meaningfully.

Cold start is still the first impression for Explore/SQL

Chat is immune (in-memory), but a visitor's first Explore click on a paused Aurora waits ~15–30s. Mitigation: P4 warming UX; and the demo banner sets expectations. If analytics show it hurts, D3-B (always-on consolidation) is the escape hatch.

Public data exposure

Removing login makes the datasets world-readable. They're public NSW housing datasets — no PII — and the existing scrub layer (scrub.py) stays. Worth a one-time confirm before flipping DNS.

In-memory limits reset on instance recycle

App Runner can recycle the single instance, wiping counters. Acceptable at this scale — an attacker gains a fresh window, still against a capped instance. WAF is the upgrade if it matters.

Two prod personalities to test

Demo vs google mode doubles the prod matrix. Mitigation: make smoke gains a demo-mode variant (chips answer, free-text path, 403 on admin, rate-limit 429) so CI covers both.

Employers might think it's all canned

The inverse risk of caching. Mitigation: the banner's honesty + genuinely live Explore/SQL. "Recorded agent, live warehouse" is a stronger story than pretending everything is live.

09Visitor analytics: who's using the demo, and how

Your question — "is it Google Analytics?" — no, and deliberately not. Your demo's audience is engineers and recruiters: the demographic most likely to run ad-blockers, which silently eat GA/GTM (often 30–40% of technical traffic). GA4 also drags in a cookie-consent banner — the exact friction this whole plan removes — and a third-party script into a portfolio piece that's meant to show self-contained craft. You already own a better pipeline.

RECOMMENDED Extend your own event log

The app already has first-party analytics plumbing: app.events (with session_id and payload jsonb — no migration), POST /events, an admin events view, and ops rollups. Add a tiny frontend beacon (lib/analytics.ts, navigator.sendBeacon) with an anonymous random visitor_id (localStorage) + session_id (sessionStorage). Same-origin API call — invisible to ad-blockers, no cookies, no consent banner, no PII, $0/mo. And it's a meta-showcase: the demo measures itself with its own event system.

  • demo_landing_view · demo_enter_click — the front-door funnel
  • page_view {tab} · chip_click {question} · chat_free_text {matched}
  • sql_run · explore_dataset_open · golden_open · theme_change
  • outbound_click {github|linkedin} — the conversion that matters

Surfaced in a dedicated Analytics tab (admin-only nav entry — invisible to demo visitors), identical in dev and prod, each showing its own environment's data. Dashboard spec:

  • KPI row — total visitors, today's uniques, returning %, sessions, avg session length
  • Funnel — landing → enter → first question → SQL/Explore touch → GitHub click
  • Activity — events/day timeseries split by surface (chat, SQL, Explore, goldens, ops)
  • Top questions — chips clicked + free-text asked, including unmatched misses (the recording backlog)
  • Recent activity feed — last N sessions as event streams

Built the dogfood way: the tab renders page objects through the app's own report engine — stat tiles, timeseries, tables — so the analytics dashboard is itself a demo of the product's rendering system.

What about the alternatives?

  • Google Analytics 4 — free, but blocked by the audience you care about, consent-banner friction, third-party script, and wildly over-featured for a portfolio funnel.
  • Plausible / Fathom (hosted) — privacy-friendly and blocker-resistant, but ~US$9–14/mo — more than half the entire demo budget for less than the event log already gives you.
  • Umami / Plausible (self-hosted) — $0 licence but needs an always-on host + its own DB: exactly the infra this plan is deleting.

Edge backstop: CloudFront logs

Enable CloudFront standard logs → S3 (pennies/mo). They catch landings that bounce before JS runs and raw attack traffic — query ad-hoc with Athena. This is the "server logs" truth the beacon can't see; between the two you have full coverage.

Privacy posture: random ids, no PII, IPs only in edge logs — add one quiet line to the landing card's fine print: "anonymous usage analytics". Good faith, no banner needed.

The owner door — reaching an admin tab in a no-login prod: demo mode removes the public login, not the auth system. A non-advertised /login route keeps the Google sign-in for admin_emails only; signing in there yields the normal admin JWT, which unlocks the Analytics tab (plus admin/ops write views) in the same session. Visitors never see the route; the demo JWT's viewer role 403s the analytics endpoints server-side.

Identity without login — how an anonymous visitor gets an id, and how repeats are counted

No login means no account identity — so the beacon mints its own, the same way every analytics tool does it, just first-party. On first load, lib/analytics.ts generates a random crypto.randomUUID() and keeps it in the browser. Two ids, two lifetimes:

SignalLives inLifetimeWhat it answers
visitor_idlocalStorageMonths — survives tab close, reboot, revisit Repeat visitors. Same id arriving on a later day = a return. Daily uniques = distinct ids; returning = ids seen on >1 distinct day.
session_idsessionStorageOne tab — dies on close Visits. New session_id + existing visitor_id = the same browser coming back. Groups a visit's event stream for the funnel.
first_seen / last_seenServer — app.eventsForever Derived per visitor_id with plain SQL (min/max(created_at)): new vs returning classification, gap between visits, "came back after the interview" signals.

Honest limits (identical to GA's, minus the cookie)

The id identifies a browser, not a person: the same recruiter on phone + laptop counts as two visitors; incognito or cleared storage mints a fresh id; two people on one machine count as one. Every anonymous analytics tool has exactly these limits — GA just uses a cookie where this uses localStorage. At portfolio scale (tens of visitors), this resolution is plenty.

What we deliberately don't do

No fingerprinting (canvas/UA hashing) to "improve" repeat detection — it's privacy-hostile, GDPR-gray, and pointless at this scale. If localStorage is blocked (hardened privacy modes), degrade gracefully: sessionStorage only, so that visit counts as unique-but-unrepeatable. CloudFront logs give an IP-based coarse cross-check of uniques — rougher (shared/rotating IPs), fine as a sanity bound.
