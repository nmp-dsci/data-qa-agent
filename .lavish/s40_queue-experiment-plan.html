03What "production AI" means for backpressure — the primer

The concepts this build teaches, each mapped to where it lands in the code. An unbounded queue is not backpressure — it's a latency bomb that converts overload into infinite wait times. Real backpressure is refusing work early and cheaply so accepted work stays fast.

1 Bounded queue + admission control

Cap the queue depth. When depth ≥ QUEUE_MAX_DEPTH, reject at the door with 429 + Retry-After in ~1ms instead of accepting a job that will time out 5 minutes later. Fast failure is a feature: the client can back off, retry elsewhere, or show "busy".

2 Little's law: L = λ·W

Queue length = arrival rate × time-in-system. With one worker at ~60s/answer, λ of 2/min means W grows without bound — no queue size fixes throughput. The experiment verifies this live: measured L, λ and W from your own runs should agree. It's also how you size QUEUE_MAX_DEPTH: depth ≈ workers × (acceptable wait ÷ service time).

3 Queue depth is the autoscaling signal

LLM work is IO-bound — CPU sits near idle while the model streams tokens, so CPU-based autoscaling (App Runner's only mode) never fires. Depth (or depth ÷ workers) is the correct signal — this is exactly the KEDA / SQS-backlog-per-instance pattern, demoed here with a tiny compose-scale watcher.

4 Deadline propagation & cancellation

Each job carries an absolute deadline. A worker picking up a job whose client already gave up must drop it, not burn 60s of LLM tokens answering nobody. Client disconnect → cancel marker → worker checks between steps. This is real money in LLM systems, not hygiene.

5 At-least-once + redelivery + poison jobs

Worker dies mid-job → the pending entry is reclaimed (XAUTOCLAIM) and redelivered to another worker. A job that kills every worker that touches it (poison) goes to a dead-letter stream after N deliveries instead of looping forever. Chat answers are side-effect-light, so redelivery is safe — but the run row must not duplicate (idempotency by job id).

6 Streaming × queueing (the LLM twist)

Latency splits into queue wait + service time, and the user sees both. The SSE contract already has status frames — the backend emits queued (position N) immediately, so waiting is visible instead of a dead spinner. TTFT/TTFP becomes queue wait + first model token: the honest number to report.

7 Per-replica vs global limits

The demo concurrency gate (app/main.py:163-230) is per-process state — valid only because prod pins one instance. Scaling multiplies it silently (N × 20). Real limits must live in a shared store; the queue itself becomes that shared, globally-bounded thing.

8 Warm-up & readiness gating

Each fresh replica pays a cold-start tax: lazy ONNX embedding load + first Node/Pyodide spawn. A worker must warm up before consuming (lifespan pre-load + healthcheck), or your p99 eats a fake 10s spike every time a container recycles.

9 Retries need idempotency

The blocking hop already retries safely because the agent writes nothing (agent_client.py:90). Behind a queue, "safe to retry" must be re-derived: enqueue is idempotent by job id; a worker dying mid-stream restarts the answer from frame zero — the relay must signal a restart, not splice two half-answers.

What each new service does

Four new containers total. agent-worker is covered above (same data-agent image running the consumer loop instead of the HTTP server); the other three:

redis the queue itself

The coordination point that lets N workers share work without knowing about each other. It holds three kinds of streams: agent:jobs — the shared job queue the worker consumer group reads, which is what provides the ack / pending / redelivery / XAUTOCLAIM semantics this whole experiment is about; agent:frames:{job_id} — one small stream per job that the worker publishes SSE frames into and the backend relays to the browser; and agent:dlq — where poison jobs land after MAX_DELIVERIES. Plus cancel:{job_id} flags for client disconnects. In-memory, no persistence: losing Redis loses queued jobs, which is acceptable here — users just re-ask.

prometheus the metrics collector

Turns instantaneous numbers into time series. Every few seconds it pulls (scrapes) the /metrics HTTP endpoints that backend-api and each worker expose via prometheus_client — queue depth (from XLEN/XPENDING), shed and provider-429 counters, queue-wait and service-time histograms, per-worker jobs processed — and stores them locally. Nothing pushes to it; services just expose a text endpoint and Prometheus finds them via ops/prometheus.yml. That history is what makes "queue depth during the E7 burst" a graph instead of a number you happened to glance at.

grafana the dashboard on top

The UI that queries Prometheus (its only datasource here) and renders the committed queue dashboard — depth, per-worker throughput, shed rate, wait vs service time — at localhost:${GRAFANA_HOST_PORT:-3000}. Provisioned from ops/grafana/ so the dashboard exists on first boot, no clicking around. This is where you watch an experiment run live, and where the s41 write-up's screenshots come from. Distinct from the ops deck (business-level history from app.load_tests) and Jaeger (per-request traces): Grafana is the second-by-second operational view.

04bRedis Streams vs AWS SQS — what actually changes

The question this answers: if the D1 build moved to AWS-managed queueing (the M4 design note, per D5), which boxes move, which disappear, and which appear? The worker-loop shape is identical in both — receive → deadline check → work → publish frames → ack. What changes is who implements the resilience semantics (you, vs the service) and, critically, where result streaming lives: Redis Streams covers jobs and frames with one primitive; SQS is fire-and-forget delivery only, so a second transport appears.

UNCHANGED what transfers 1:1

The worker loop shape (receive → deadline check → work → publish → ack), admission control at the door, idempotent run persistence by job_id, the queued-position UX, and the whole metrics/dashboard story. Everything M1–M2 teaches is the vocabulary SQS speaks — just with different verbs.

SQS GIVES FREE most of M2 disappears

Crash reclaim (visibility timeout), delivery counting, DLQ redrive, durability, multi-AZ, IAM auth. Roughly all the reaper/heartbeat code M2 builds by hand is a queue attribute in SQS — which is exactly why building it by hand first is the better learning order.

SQS TAKES AWAY streaming, precision, iteration speed

The big one: no per-job result stream, so the single-primitive architecture splits into queue + result transport — and the most common choice for that transport is… Redis (ElastiCache). Depth also degrades from exact/instant to approximate/minute-lagged, which softens both admission control and the autoscaling signal.

WHY THIS ORDER build Redis, document SQS

Per D1 + D5: hand-roll the semantics locally where iteration is instant, then write the M4 mapping note instead of deploying. In an interview, the table above is the answer to "how would you run this on AWS?" — same loop, managed resilience, plus an explicit story for the streaming gap.

REVIEW Is this a fair test? Yes — with the right claim attached

Fixing S removes provider noise (the exact reason the stub was originally recommended), one-shot users make the offered load exact, and sweeping N across the capacity line (5 under, 10 near, 20 over for 1–3 workers) exercises both regimes. Best of all it's falsifiable: ⌈N∕W⌉×S is the prediction, and measured-vs-predicted is stronger evidence than any before/after anecdote. The one framing caveat: a one-shot burst measures burst capacity and makespan, not steady-state throughput — Little's law needs sustained arrivals, which stays the E-runs' job. Say "handles a 20-user burst" not "handles 20 users/minute", and the claim is airtight.

TWEAKS four amendments to keep it honest

① Hold everything but the swept variable identical across cells and repeat 3× (stub runs are free). ② Set QUEUE_MAX_DEPTH=32 for C-runs — at the default bound of 10, a 20-user burst sheds ~half the users and the comparison silently becomes "queued did less work"; shedding gets its own run (E7). ③ The stub must stream frames across its S seconds (progress → pages → result), not sleep(S) then dump — otherwise TTFP is meaningless and the relay path isn't exercised. ④ In C1, count timeouts as failures in the chart, not as missing data — the direct path's failure mode is the point.

SUCCESS CRITERIA

① E5/E6 show ≥ 1.8× / ≥ 2.5× throughput lift over E4. ② E7 holds accepted-job p95 within ~15% of E4 while shedding cleanly. ③ E8 loses zero jobs. ④ Measured L ≈ λ·W within ~20% (Little's law sanity check). ⑤ Every run lands as a row in app.load_tests with workers + queue_mode dimensions, visible on the ops deck. ⑥ C3/C4 makespans land within ~15% of the ⌈N∕W⌉×S prediction (median of 3). ⑦ E9's live shape (TTFP, service-time spread) resembles the stub's — report it with n, it's the only small-sample run.

What carries jobs from backend to workers, and frames back?

Redis Streams (hand-rolled)

Consumer groups + XAUTOCLAIM + per-job frame streams. ~200 lines you fully understand.

  • Teaches ack/pending/redelivery/DLQ semantics for real — the learning goal
  • One primitive covers jobs AND frame relay
  • Industry-recognizable (Redis 64%-adjacent in your skills notes via Docker/infra)
  • New container; you own edge cases a framework would handle

arq (Redis, framework)

Asyncio-native job library on Redis.

  • Retries/timeouts free; less code
  • Hides exactly the semantics you're trying to learn
  • Frame streaming still needs hand-rolled pub/sub anyway

Postgres SKIP LOCKED

Jobs table + FOR UPDATE SKIP LOCKED + LISTEN/NOTIFY.

  • Zero new infra; transactional with the run row
  • Frame relay is clunky (NOTIFY 8KB limit → notify-and-fetch)
  • Polling workers; adds load to the very DB you're measuring

AWS SQS

The real prod answer on AWS.

  • Managed, durable, the interview name-drop
  • Slow local iteration, no streaming story, prod is demo-mode (no agent deployed)
  • Better as the M4 "how this maps to AWS" note than the build

08Risks & open questions

RISK

Laptop is the hidden ceiling

3 workers × sandbox subprocess (Pyodide cold-starts pandas per run) on one machine — CPU contention can masquerade as "queue overhead" and flatten the E5/E6 lift. Mitigation: record host CPU during runs (the Grafana node view helps here) and report worker-side service time separately from wait.

RISK

DeepSeek's rate limiter — contained to E9 after the D2 re-decision

With E2–E8 and the C-series on the stub, provider throttling and latency variance touch only the E9 validation run. Keep E9's λ tiny, tag provider 429s/timeouts as their own counter (never fold them into our error %), and record its token spend. If E9's shape diverges from the stub's, tune STUB_LATENCY_S / the frame cadence to match reality and note the correction in s41 — that's calibration, not failure.

RISK

Postgres connect storms under NullPool

Every query = fresh TCP+TLS connect; N workers amplify it. If E1 knees on connects, either accept and document it (it's a finding, not a failure) or bolt PgBouncer on as a follow-up experiment. Don't switch the app to pooled engines mid-experiment — it changes the system under test.

RISK

Mid-stream worker death UX

Redelivery restarts the answer from frame zero. The relay must truncate + signal status: restarted; the frontend already tolerates status frames, but verify it doesn't render two half-answers. E8 exists to prove this.

RISK

Redis is a new single point of failure

Fine for a local experiment (that's also true of SQS's role in prod — the queue being the SPOF is the standard trade). No persistence config needed; jobs are re-enqueueable by the user.

OPEN

Which non-chat endpoints route through the queue?

Proposal: chat (/agent/ask*) only. /agent/sql and /agent/schema stay direct (they're the fast workload-A surface and the SQL editor needs low latency). Golden authoring / eval endpoints stay direct too — they're admin tools. Confirm or annotate.

OPEN

Does the blocking /ask endpoint also go through the queue?

Proposal: yes — it enqueues and blocks on the final result frame (same machinery, no second path). Slack and service-account callers then get backpressure for free.
