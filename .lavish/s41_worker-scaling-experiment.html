Does adding workers actually shrink the queue?

A 3×3 sweep — 1 / 3 / 5 workers × the data-agent taking 10 / 30 / 60 s per answer — with a fixed burst of one-shot users, measured against a closed-form prediction. Alongside it: the production metrics an engineer would actually watch (latency percentiles + CPU/memory), wired into the existing Grafana deck.

PREDICTION WE'RE TESTING

makespan ≈ ⌈N ÷ W⌉ × S — with N users in a burst, W workers, and S seconds of service time, the burst drains in ⌈N/W⌉ serial "waves". Going 1 → 5 workers should cut total drain time ~5×, and the already-run smoke agrees: 4 users × 1 worker × 10 s stub measured 41.3 s ≈ 4 × 10 s. This sweep tests whether that linearity holds across the whole grid — and where it bends.

GOTCHA Deadline must outlive the worst wait

W1-S60's last job waits 840 s. The default JOB_DEADLINE_S=240 (app/config.py:35) would expire 11 of its 15 jobs in the queue — by design. Every cell runs with JOB_DEADLINE_S=1200 and the prober's --deadline-s 1500.

GOTCHA Depth must not shed

Default QUEUE_MAX_DEPTH=10 would 429 five of the 15 users and corrupt the capacity measurement. All cells run at QUEUE_MAX_DEPTH=32 — same fairness rule the s40 C-series locked. Shedding is E7's experiment, not this one.

02 Serial or concurrent? What one worker really does

Your question — "does the data-agent work through each request one at a time, or can one worker handle multiple requests since it's an async LLM react loop?" — has a two-part answer, and the distinction is exactly what this experiment leans on.

Today: one queue worker = deliberately one job at a time.

The worker loop reads count=1 and awaits the job to completion before reading again (agent/worker.py:237–249, and its docstring says so out loud). That's a choice, not a limitation of the runtime: it makes capacity arithmetic honest (1 worker = 1 answer-slot, so ⌈N/W⌉ is exact), keeps memory per replica bounded, and avoids contention on the sandbox subprocess, which is real CPU work.

But yes — the react loop is mostly waiting, so one process could interleave.

In a live answer, most wall-clock is spent awaiting DeepSeek over the network. The whole agent is asyncio end-to-end — the HTTP data-agent service already serves concurrent requests on one process, and the sandbox's blocking run_code was moved off the event loop in M0 (asyncio.to_thread, agent/main.py:954–1376). A worker with a concurrency semaphore of, say, 4 would run 4 react loops at once, overlapping their LLM waits — one replica behaving like ~4 workers for I/O-bound time, while CPU-bound sandbox slices still serialize through the thread pool.

04 The runner: one command, nine cells, one results file

A new scripts/wsweep.py drives the whole grid so the sweep is reproducible and boring. No k6 needed — scripts/loadgen_sse.py (already built, already used for the smoke) is the load source, so this runs on this machine today.

for W in 1 3 5:                 # outer: restacks are slow, latency changes are free
  for S in 10 30 60:
    1. restack:  QUEUE_MODE=on LLM_STUB=1 STUB_LATENCY_S=$S QUEUE_MAX_DEPTH=32 JOB_DEADLINE_S=1200 \
                   docker compose up -d --no-deps --scale agent-worker=$W agent-worker backend-api data-agent
    2. wait:     all workers heartbeating (consumer count via XINFO CONSUMERS) + backend /health
    3. mark t0, run:  loadgen_sse --users 15 --deadline-s 1500 --json out/w$W-s$S.json
    4. snapshot: Prometheus query_range over [t0, now] — wait p95, service p95, jobs/min,
                 CPU%/mem per container — folded into the same JSON
    5. record:   row into app.load_tests via scripts/ops_ingest.py
                 (notes: "wsweep workers=$W stub_s=$S users=15", no schema change)

then: render results table (measured vs predicted makespan, % error) → s42 artifact

Fairness rules carried from s40

  • Same build for every cell — only env changes
  • Workers warmed before t0 (WARMUP_ON_START already in the worker boot)
  • No shedding in capacity cells (depth 32)
  • One cold throwaway probe after each restack, excluded from results

What "yes" looks like

  • Measured makespan within ~10 % of ⌈15/W⌉×S in all 9 cells
  • Queue-wait p95 collapses with W while service p95 stays flat ≈ S
  • Grafana: depth sawtooth drains 3× / 5× steeper as W rises

What would bend the line

  • Relay/SSE fan-in on one backend process (15 concurrent streams)
  • Postgres pool limits when 5 workers persist at once
  • Docker Desktop CPU throttling with 5 warm replicas (~150 MB each)

Any bend is a finding, not a failure — it's the next bottleneck named.

RISKS Known limits of the rig

  • cAdvisor on macOS reads the Docker Desktop VM — per-container CPU is accurate within the VM but a few host metrics are absent. Fine for our purpose.
  • All replicas share one laptop — CPU panels show shared-core behaviour, not the isolated-node behaviour App Runner would give. The s40 §04b AWS note covers the mapping.
  • Stub ≠ live — service time is exact by construction. That's the point (it isolates queueing behaviour), but every claim gets labelled "stubbed" and one live cell validates the machinery.
