Review of the idea

Does it make sense? Yes — and it's a smaller build than it sounds

Confirmed: MLflow wins for this goal set. It is the only one of the three that covers the full cycle you want — registry + aliases, run/metric comparison, trace capture, and eval tooling — self-hosted for $0, and it's the harness you already run in ConvFinQA-agent (ghcr.io/mlflow/mlflow:v3.12.0). The linchpin fact, verified against the MLflow docs: the OSS tracking server ingests OpenTelemetry traces natively (OTLP/HTTP at /v1/traces, MLflow ≥ 3.6). Both services here already emit OTel spans through an additive OTLP_ENDPOINT — so "tracing in MLflow, not Logfire" is a re-point, not a re-instrumentation.

Adjustment 1

"Registry of agents" here means registering the agent build fingerprint, not model weights. app.agent_versions (s24) already composes exactly the right identity: provider + model + prompts-hash + skills-hash + knowledge-hash + git sha + image tag. Register that as the model version; artifacts are the spec, not a pickled model.

Adjustment 2

Postgres stays the operational source of truth (app.agent_versions, eval_runs, eval_results already exist and the app UI reads them). MLflow is the MLOps view + promotion mechanics — mirror into it, don't migrate onto it. Same reasoning as ConvFinQA's registry.json: the app must render without a tracking store.

Adjustment 3

Prod runs demo mode with no data-agent service — replayed answers, no live agent to trace or score. So champion/challenger is a dev + CI activity today. Build the harness dev-first (M0–M3); prod hosting of MLflow is a deliberate later step (M4), not a blocker.

Why the tracing switch is nearly free

Logfire's SDK is an OpenTelemetry SDK; the instrumentation (instrument_pydantic_ai, instrument_fastapi, instrument_httpx) stays exactly as-is and Logfire Cloud stays off (the token is already empty). Only the export destination changes:

# services/data-agent/agent/otlp.py — today
OTLPSpanExporter(endpoint=f"{endpoint}/v1/traces")

# M1 — same exporter, MLflow destination + experiment routing header
OTLPSpanExporter(
    endpoint=f"{endpoint}/v1/traces",          # OTLP_ENDPOINT=http://mlflow:5000
    headers={"x-mlflow-experiment-id": os.environ["MLFLOW_TRACE_EXPERIMENT_ID"]},
)

Same one-line change in backend app/tracing.py:_otlp_processors(). Because processors are additive, Jaeger can be kept as a second destination during the transition, then dropped (decision D2 below).

The honest trade: you give up Logfire's alerting/live-ops polish for a single self-hosted plane. In dev that costs ~nothing (Jaeger goes away too). If prod observability ever needs alerting, OTel dual-export means MLflow + anything-else is additive, not a cutover — the harness you're building doesn't foreclose it.

Why not Phoenix + Jaeger, like the ConvFinQA self-host advice?

It is the same architecture — the difference is only which viewers subscribe to the span fan-out. ConvFinQA's own eval-loop plan (.lavish/s04) examined exactly this and landed where this plan does: MLflow as the primary trace store (it verified mlflow/server/otel_api.py, /v1/traces and the x-mlflow-experiment-id constant in the venv), with Arize Phoenix rated "best second opinion" — one container, OTLP in, strong LLM trace UI — run alongside as a cheap insurance policy for a few weeks because MLflow's trace explorer is younger, then kept only if you actually open it.

  • Phoenix and Jaeger are viewers, not the cycle. Neither has a model registry, aliases, or eval runs — with them you'd still run MLflow for ⅔ of this ticket's goal, just with two more containers.
  • Adding Phoenix later is one env var, not a migration. The exporters are additive span processors; a second OTLP destination (Phoenix on :6006) subscribes to the identical spans. Decision D2 below now carries this option.
  • Jaeger is already here — it's today's general-trace viewer, and D2 decides whether it stays as dual-export or retires once MLflow traces are verified.
  • License note from the ConvFinQA review: Phoenix is ELv2 — source-available, fine for internal self-hosting, not OSI open source.

Full-coverage production observability

The distilled model — and your four-way split, refined

Your split (request tracing · LLM · p95/CPU/mem/network · cost) is close. The standard model separates what you collect from what you ask of it — that's what makes the tool mapping fall out cleanly.

SIGNALS · what you collect

MELT: Metrics (aggregates over time), Events, Logs (discrete records), Traces (one request's path across services). Your bucket 1 is the T; your bucket 3 is two different uses of M. Everything below is one of these four, correlated by trace/request id.

LENSES · what you ask

RED for request-driven services (Rate, Errors, Duration — p95 lives here). USE for resources (Utilization, Saturation, Errors — CPU/mem/network/ACU live here). Google's 4 golden signals = the two combined (latency, traffic, errors, saturation). GenAI lens (OTel GenAI semconv): spans per LLM/tool call, tokens, cost-per-answer, quality evals. FinOps lens: infra $ + LLM $.

PRACTICES · how you act

SLOs + error budgets (alert on burn rate, not every blip), dashboards per audience, correlation habit (metric spike → trace → log line), synthetics (is it up before a user tells you), retention/cardinality discipline.

Direct answers to the tool question

  • "MLflow for LLM, Grafana for requests?" — yes, that's the right shape. MLflow owns the GenAI lens (per this plan) and receives the request-flow traces, since both ride the same OTel stream (M1).
  • "Could this be Jaeger?" — no. Jaeger is a trace viewer: it answers "why was this one request slow?" It has no aggregates, dashboards, or alerting — it cannot tell you p95 rose 40% this week. That's the metrics plane (Prometheus + Grafana in dev, CloudWatch in prod). Traces and metrics are different signals; you need one tool per role, not per product.
  • GPU: not applicable here. The LLM is API-based (DeepSeek) — there's no local inference, so "GPU" collapses into LLM cost + latency per call, which query_runs and MLflow already carry. It becomes a real pillar only if you ever self-host a model.
  • What your split was missing: logs, SLOs/alerting, and uptime synthetics — rows 5–8 below. You already have more of them than you might think (/ops deck computes availability + responsiveness SLOs from Postgres today).

Risks & failure modes

What could bite

Streaming spans in autolog
MLflow's pydantic-ai autolog has an open FR for streaming support, and the agent answers via /agent/ask/stream. M1 sidesteps this entirely (Logfire's instrumentation already handles streaming; MLflow only receives OTLP). Re-check before adopting autolog in M4.
Double instrumentation
Never run Logfire's instrument_pydantic_ai() and mlflow.pydantic_ai.autolog() in the same process — duplicated spans and token counts. M0–M3 keeps exactly one SDK (Logfire's, as today).
Port and profile clashes
ConvFinQA's MLflow owns host :5000; this one binds :5500 (MLFLOW_HOST_PORT, same pattern as the :8010 backend remap). Keep the service in the default profile (the eval loop needs it), not behind obs.
Trace volume & retention
Every dev question now lands spans in sqlite. Fine at this scale (ConvFinQA precedent); add a make mlflow-gc (mlflow gc) target and revisit Postgres backend only if the file gets unwieldy — decision D3.
Eval writes diverging
MLflow sink must be additive and soft-fail: DB write (existing) is primary, MLflow logging wrapped so a down server never fails make eval. Runs carry eval_run_id as a tag so the two stores reconcile.
Unauthenticated UI
Dev binds localhost only (like Jaeger/Grafana today). Prod exposure is M4-only and goes behind admin auth — never a public App Runner URL.
Prod value is limited today
Named openly: with demo mode on, the harness improves the development cycle now and prod later. That matches the stated goal ("build the harness, optimise down the track").
