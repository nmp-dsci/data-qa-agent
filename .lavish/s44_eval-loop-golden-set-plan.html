Current state — what one eval already does

The agent is one loop; the grading is already split

Production answering is a single autonomous run: the model calls extract(sql) (governed SQL, self-correcting, up to 8 attempts), then run_analysis(code) (pandas sandbox that computes headlines and builds the report pages). The eval runner replays the golden question through the real POST /ask path — RLS, caps, persistence — and grades four pillars from the persisted run:

Your architecture question

Keep SQL + viz together, or split the agent?

recommended Keep the product together, split the evaluation

Production answering stays one autonomous loop — that's the product. Evaluation already splits: G1 grades SQL alone, G2/G3 grade viz alone. A golden is curated in two independent halves you can edit separately in the Golden tab.

add A sql_only lane on the real agent

For fast SQL-golden iteration: run answer_with_sandbox() with only the extract tool registered and stop on first success. Same system prompt, same self-correction, same knowledge — ~1–2 LLM turns instead of ~20, no judge cost.

rejected Reuse /agent/sql/assist

It looks like the answer (NL→SQL endpoint exists today) but it's a different, simpler code path — no extract-tool self-correction, no entity lookup, different prompt. Scoring it would grade a generator production never uses.

Risks & honest limits

What could bite

Marts are monthly aggregates
No per-sale rows ⇒ no price-band histograms or days-on-market. Every question above was authored to the real grain; anything a reviewer adds must be too.
sql_only prompt divergence
A model that knows it won't build a report may write slightly different SQL. Mitigation: sql_only is an authoring/iteration lane only; official scores always come from the full /ask path.
Ground truth is recomputed live
golden_truth() re-runs golden_sql each eval — baselines move with data reloads by design. Tolerances (tolerance_pct) absorb drift; pack-lint catches breakage.
Dev DB debris
eval_cases holds e2e leftovers (case_key IS NULL). Phase A cleans them; the YAML pack stays the reviewed source of truth.
Judge cost ×24 new cases
Full judged runs only at milestones; day-to-day iteration uses SQL_ONLY=1 / NO_JUDGE=1. Per s43, cost is cache-dominated — cut turns, not prompts.
Un-calibrated judges
insight-v1 (and the new viz-v1) stay advisory until Phase E shows judge↔human agreement — no LLM score gates pass/fail before then.
