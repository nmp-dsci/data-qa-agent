s45 · plan for review · branch agent_sdk

Move the data agent onto the Claude Agent SDK

The data agent is a ReAct loop — one LLM making tool calls — currently driven by pydantic-ai over DeepSeek. This plan swaps the loop engine for the Claude Agent SDK (Python), running on the Claude subscription, moves knowledge / grounding to filesystem-native patterns, and keeps everything else — sandbox, SQL guardrails, pages contract, evals, infra — byte-for-byte identical. Success = 5 golden questions answered through the app with the new runtime, reproducing today's outputs.

rewrite ≈ 1.9k LOC untouched ≈ 7.8k LOC side-by-side rollout, flag-gated MLflow champion / challenger ready decided: prod stays demo mode — no API-key prod
Goal

Recreate the status quo — only the loop engine changes

What changes

The agent runtime: pydantic-ai's Agent.run() tool-loop → Agent SDK query() with in-process MCP tools. Knowledge lookup moves from bespoke tools to filesystem Read/Grep over a per-run workspace. Auth moves from DeepSeek API key → Claude subscription token.

What must not change

The /agent/ask + SSE contract (plan / page / progress / status / result frames), the AgentAnswer & report.pages shapes, SQL guardrails + RLS, the sandbox, query_runs persistence, make eval, the frontend.

Definition of success

5 questions run through the app on the agent_sdk runtime and reproduce outputs similar to what the app already gives — graded by the existing deterministic graders + judge, and eyeballed side-by-side in the browser. Details in the success gate.

Current state

One loop, eight tools, everything governed outside the model

There is exactly one agent architecture today. services/data-agent/agent/sandbox_agent.py (955 LOC) owns the whole loop: system-prompt assembly, tool registration, budgets, trace capture. pydantic-ai owns retries and message history; model_factory.py adds a 4-attempt backoff wrapper; budgets are tool-call quotas, not turn counts (extract ≤ 8, sandbox runs ≤ 4, knowledge reads ≤ 6, model requests ≤ 22, tokens ≤ 600k).

Target state

Agent SDK runtime + per-run filesystem workspace

A new agent/sdk_agent.py implements the same answer_with_sandbox() contract behind a runtime flag. The SDK's query() drives the loop; the four side-effecting tools stay as in-process MCP tools (governance cannot move to the filesystem); the four read-only grounding tools become files the agent explores with the SDK's native Read/Grep/Glob.

Per-run workspace layout

runs/<run_id>/ · built per request, deleted after
├─ CLAUDE.md ← workflow + two-pass plan + contract
├─ marts.md · tier 0: list_marts() rendered
├─ schema/ · tier 1: describe_table() per mart
│   ├─ mart_sales.md · mart_rent.md · mart_yield.md
├─ knowledge/ · tier 2: Insight Playbook (symlink/copy)
│   └─ *.md · grain, join keys, non-additive traps
└─ frames/ ← extract() also drops head-sample CSVs
     └─ df.head.csv · agent can Read to sanity-check

Schema/knowledge renders reuse schema.py and knowledge/ verbatim — the files are generated from the same sources the current tools read, so content parity is automatic and knowledge_version() hashing still applies.

The CLAUDE.md is an optimisable artifact. It's rendered per run from a versioned template in the repo (agent/prompts/workspace_claude.md) — the agent-sdk runtime's equivalent of the system prompt. Its hash feeds the av-* fingerprint, so every CLAUDE.md or prompt edit is a new challenger version the eval pack can score: prompt and CLAUDE.md are both levers in the optimisation loop.

Built-ins restricted via tools=["Read","Grep","Glob", "mcp__dp__*"] — no Bash, no Write, no WebSearch. The workspace is the agent's entire visible filesystem (cwd pinned there).

Auth — decided. The agent_sdk runtime runs on the Claude subscription via claude setup-token → CLAUDE_CODE_OAUTH_TOKEN in the local data-agent container, and it is local/dev-only: there is no API-key prod version — prod stays demo mode, which already deploys no data-agent service at all (recorded answers only), so nothing about the prod topology, Terraform, or quota changes. Notes that still matter: personal dev use of the subscription token is the SDK docs' grey zone (they steer products to API keys); subscription rate limits are shared with interactive Claude Code use; and if both ANTHROPIC_API_KEY and the OAuth token are set the API key wins, so the container env must set exactly one.
Investigated alternative

Keep pydantic-ai and put Claude Code under it?

Asked and investigated: instead of replacing pydantic-ai, can it be used with the Agent SDK? Yes, mechanically — a community bridge, pydantic-ai-claude-code (v0.8.1, Oct 2025, beta), registers the local Claude Code CLI as a pydantic-ai model provider: the existing loop, tools, and traces stay, only model_factory.py learns a claude-code:sonnet spec. The two loops can't be merged the other way round (pydantic-ai inside the SDK = two competing agent loops). Side-note either way: Logfire has a first-party Claude Agent SDK integration, so the current logfire instrumentation story survives a full migration too.

option A Bridge: pydantic-ai loop, Claude Code as model

  • Cost: tiny — ~50 LOC in model_factory.py; sandbox_agent.py, traces, evals untouched.
  • But: a beta, single-maintainer package in the critical path; OAuth token expires ~7h in long-running processes (bad for a server); one CLI subprocess per model request (×~15 per run).
  • And the point is lost: Claude Code is reduced to a completion endpoint — no filesystem knowledge base, no SDK hooks, no skills. The "migrate tool calls to filesystem" goal dies; this is a model swap, not an Agent SDK migration.

chosen Full Agent SDK runtime (this plan)

  • The goals — filesystem knowledge, SDK-native tracing/hooks, subscription runtime, Architecture tab — live in the SDK's loop, not in its model call.
  • First-party SDK, one subprocess per run (not per request), and the pydantic-ai champion stays runnable side-by-side for A/B.
  • Verdict: option A is the documented fallback if the SDK migration stalls at M0, not the plan.

After the gate

The optimisation loop the logging pays for

Scope discipline: this migration just implements the agent_sdk runtime — the loop below is not built now. But because M3 logs every run's return (answer, pages, scores) next to its path (trace) in MLflow, the loop becomes a query away rather than a new build:

1 · Score accuracy

Every run (live or eval) carries grader + judge scores as MLflow metrics per agent_version_id — accuracy over time per runtime/model/prompt-hash, straight off the champion/challenger dashboard.

2 · Mine traces for ideas

Filter low-scoring runs, read their traces: wasted knowledge reads, SQL retry patterns, pass-2 failures. eval_diagnose.py's failure clustering already does this offline — MLflow makes it browsable per version.

3 · Ship a challenger

Each improvement idea (prompt tweak, CLAUDE.md edit, new skill, quota change) = new av-* fingerprint → run the golden pack → mlflow_registry.py promote if it beats the champion. Goldens stay the training signal.

Success gate

5 questions, graded like any challenger

Selection

Pick 5 goldens from app.eval_cases that the current champion passes (parity needs a passing baseline), spanning marts and the tier ladder — e.g. one T1 scalar (sales), one trend series (rent), one breakdown (yield), one compare, one insight-tier question. Final ids picked at M4 from the latest eval run.

Mechanics

  1. AGENT_RUNTIME=agent_sdk on the data-agent service, restart.
  2. scripts/eval_run.py limited to the 5 cases → replays through the real /ask path, tagged with the challenger fingerprint.
  3. scripts/eval_compare.py champion-vs-challenger on those cases.
  4. Ask the same 5 in the browser; screenshot side-by-side (pages render, charts ordered, ghost slots fill).

Pass criteria — "similar to existing outputs"

  • must deterministic graders (scalar/row-set/series/extraction) pass on all 5 — same numbers out of the same governed SQL.
  • must grade_presentation_format + structural lint pass — same page/object shapes.
  • must zero guardrail violations; RLS intact; no budget hard-stops.
  • target judge rubric score ≥ champion − 0.5 on the 5-criterion rubric (wording may differ; insight quality must not regress).
  • target wall-clock and turns within 1.5× champion; ttfp_ms recorded for the A/B.

Not required for success: matching prose verbatim, matching DeepSeek's tool-call order, or migrating the single-shot call sites (titles, sql_assist, codegen, judge).

Risks & open questions

What could bite

decided Subscription-auth scope

No API-key prod version — prod stays demo mode (no data-agent service deployed). The subscription token serves local dev + the gate only. Residual watch-item: gate runs share your interactive Claude Code quota, so schedule eval runs accordingly.

risk Two-pass protocol drift

A stronger model may try to do everything in one pass or over-explore the workspace. Mitigation: CLAUDE.md is explicit about pass 1/pass 2; hooks enforce the same quotas that tamed DeepSeek; the budget hard-stop pattern is preserved. And because the CLAUDE.md is generated from a versioned template, any drift fix is itself an optimisable, fingerprinted prompt change.

risk Trace fidelity gaps

SDK message stream may not expose every retry/validation event pydantic-ai did. Mitigation: hooks capture every tool in/out; accept a slightly coarser retry record; inspect_run.py is the acceptance test.

risk Per-request CLI subprocess

Spawn latency + memory per concurrent ask on App Runner. Mitigation: measure at M0; queue path already bounds concurrency via worker slots; s41 showed 1 process × 4 slots is the sweet spot.

open Data egress

Rows now flow to Anthropic instead of DeepSeek — for this public NSW dataset that's fine, but note it in AGENTS.md's security model when the runtime lands.

open Judge model conflict

Judge is Claude today (cross-family vs DeepSeek). With Claude answering, keep independence by judging with a different family/model — decided at M3.
