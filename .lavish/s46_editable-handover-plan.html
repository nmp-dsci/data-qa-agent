Replacing the render layer:
the agent builds a deck, not a page

Data Pilot currently answers by emitting objects that React draws with visx. This plan moves the whole visualisation phase into Google Sheets and Slides — the agent picks a layout from a template pack, writes the data, sets the headline and commentary — and then decommissions the browser rendering stack entirely.

The honest headline

The move itself is sound and the API supports it. But the render layer is load-bearing for five surfaces, not one: chat, Explore, Template Studio, the Goldens editor and the Ops dashboard all render through the same components. Deleting it is a ~10,000-line change across the app, not a swap behind chat. Everything below is sized so you can decide how far the purge actually goes.

01 · Definition of done

What “finished” means for this migration

  • The agent answers into Sheets + Slides The agent_sdk runtime orchestrates the visualisation phase: find a layout in the pack, add the slide, write the sheet, set headline and commentary.
  • Artifacts come from a template pack Named layouts in a Slides master, swappable per use case without code changes.
  • Three golden questions prove the loop Authored fresh against the new contract, graded end to end. The existing set is decommissioned.
  • The browser rendering stack is gone report-engine, visx chart components, the object registry, the parity gate, and every test that asserts on rendered chart DOM.
  • Nothing half-migrated is left running No surface still depending on PageLayout. This is the clause with the real cost — see §08.

One sequencing recommendation, strongly held. Build the new path alongside the old one and gate the purge on the three goldens passing. Deleting first turns a migration into a rewrite with no working reference to compare against — and the only proof that a deck is correct is diffing it against what the current engine produces for the same question.

02 · What exists today

A data-first contract with exactly one renderer

The agent never emits HTML. It emits a report dict; compose_pages() (agent/pages.py:451-480) lifts that into a validated Page / PageObject tree; React draws it. Crucially the objects carry data, not geometry — chart_object_from_spec (pages.py:285-381) repacks real dataframe rows (capped at 2000, skills/charts.py:21) and visx computes scales at render time.

Why the move is possible

Rows travel inline

No server-side paths or pixel coordinates exist anywhere. Every chart is {fields, unit, rows[]} — which is what a native Sheets chart needs. Had this shipped as SVG, the plan would be “export a PNG”.

Why it is overdue

Two channels already discard it

Slack sends answer.answer truncated (integrations.py:224); the webhook sends answer/sql/row_count (:78-85). A channel= argument exists with no renderer behind it.

Why it is expensive

One renderer, five consumers

Chat, Explore, Template Studio, the Goldens editor and Ops all call the same PageLayout/ObjectBody. There is no second rendering path to fall back on.

03 · The constraint that decides the design

Native charts do not cross vendor boundaries

Text, shapes and tables round-trip almost everywhere. Charts do not. A chart stays editable only inside the vendor boundary it was authored in.

04 · Target architecture

How the agent builds a deck without burning the turn budget

You described the visualisation phase as: search the template, copy a layout into a new slide, update the attached sheet, set the headline and commentary. That is exactly right as a description of intent. The question is how many round trips it costs.

The turn ceiling is a dial, not a wall — but turn it deliberately. Everything shares one budget: max_turns=22 (config.py:132) and 600k tokens (config.py:133), enforced in sdk_agent.py:629-667. Both are already settings, so raising them for a dev-only runtime is a config change, not code. Worth keeping in view: the agent_sdk runtime measured 26–43 turns on the M4 gate against a champion's 18–28, so a visualisation phase lands on top of a run that is already the more expensive of the two. Loosening the ceiling is right; removing the per-tool counters is not — a runaway loop should still hit a wall.

One composite call per slide — the agent names the layout and fills it, in a single round trip.

The agent greps the curated catalogue — free, and exactly how knowledge pages already work — then calls add_slide(...) once per slide, naming the layout and carrying the frame, the chart intent, the headline and the commentary together. It orchestrates slide by slide and reacts to each result, which is what you described; it just does not pay a separate round trip to find a layout, add it, fill the sheet and set the text. One turn per slide rather than four, and each slide lands atomically.

The tools, alongside the existing five

GOVERNED_TOOLS = ["extract", "run_analysis", "lookup_values",

async def add_slide(

    headline:   str,
    commentary: str,
    frame:      str | None = None,   # an already-extracted frame
    chart:      ChartIntent | None = None,  # skills/charts.py vocabulary
) -> SlideResult:
    """Writes the sheet range, adds the native chart, creates the slide
    from the named layout and fills its placeholders — one atomic
    batch. An unknown or disabled layout name is rejected with the
    curated list, so a bad guess costs one turn, not a broken deck.

    Budget-capped like extract/run_analysis via the
    SandboxBudgetExhausted pattern (max_slides, default ~8)."""

Loosening the ceiling does not mean removing the counter. extract and run_analysis each carry their own per-run cap (max_sql_attempts=8, sandbox_run_attempts=4) that raises SandboxBudgetExhausted independently of max_turns. A slide tool wants the same treatment, so a confused agent produces a short deck rather than a 200-slide one.

Note what this reuses rather than reinvents. skills/charts.py already emits chart intent (mark + encoding + values) and agent/units.py already classifies currency/number/percent — which is precisely what a Sheets cell format needs. Both survive the migration untouched and become more relevant, not less.

05 · The template pack

A catalogue of layouts, edited in Slides rather than in code

Slides has a first-class concept for this. A presentation's master carries layouts; createSlide accepts a layoutId naming one, and placeholderIdMappings assigns your own object IDs to the placeholders it creates — so insertText can fill them in the same atomic batch. Verified against the Slides v1 discovery document.

Confirmed supported

What the API gives you

  • createSlide(layoutId) targets any custom layout in the copied pack's own master — not just the 12 predefined ones.
  • layoutProperties.displayName exposes the human-readable name at runtime, so the catalogue is discovered rather than hard-coded.
  • placeholderIdMappings + insertText in one batch is Google's own published sample.
  • Batches are ordered and atomic — a malformed slide fails the run rather than producing a broken deck.
Confirmed gap

Chart slots need a manifest

PlaceholderType includes CHART and TABLE, but no request fills them. createSheetsChart takes explicit EMU size + transform only — the schema has no “put this chart in that slot” field.

So the pack ships a manifest: layout name → chart-slot geometry, read once from the template and cached. Without it, every slide costs a read-then-write round trip. With it, the whole deck is one batch.

The pack is the lift-and-shift seam. A new internal workflow gets a new pack and a new dataset — not new code. That is the part of the original ask a single hard-coded template would never have delivered. Two smaller findings: speaker notes always cost a round trip (speakerNotesObjectId is not returned by CreateSlideResponse), and while files.copy duplicating masters is universal in practice, Google does not guarantee it — so assert the expected layouts exist after copying.

Pack Inspector — the curation surface

Template Studio dies with the renderer, but its job does not: you still need to see every layout and decide which ones the agent may use. That job gets better, not worse — the Inspector shows the real layouts from the real pack, rendered by Google, rather than a local approximation of them.

Curation here is prompt engineering with a UI. What you enable and how you describe it is the layouts.md the agent greps at run time. A layout with a vague “use when” line gets picked badly; that is now a thing you can see and fix without touching code.

What the Inspector is for

  • See what actually exists — every layout in the pack with its real rendered thumbnail and the placeholders the manifest detected.
  • Enable or withhold — only enabled layouts reach layouts.md, so the agent's choices are a curated set rather than whatever happens to be in the file.
  • Write the “use when” line — the single highest-leverage text in the whole feature, and the thing that decides whether layout choice is good.
  • Catch breakage early — a renamed layout or a missing chart slot shows as unmapped here instead of as a crooked deck later.
Consequence worth naming

Curation moves the fingerprint

layouts.md lives in the run workspace, and the av-* fingerprint hashes the workspace (version.py:95-124 via workspace_manifest). So enabling a layout or editing a “use when” line changes the agent version.

That is correct behaviour, not a bug — curation is a prompt change and should be visible to evals and MLflow. But it means the Inspector is an agent-versioning surface, and edits deserve the same care as editing the system prompt.

06 · One user, two modes

Dev generates. Demo replays. Prod holds no Google credentials.

This removes what would otherwise be the riskiest work. A single generating account means no authorization-code flow, no per-user consent, no refresh tokens encrypted under RLS. One long-lived token in .env, the same shape as ANTHROPIC_API_KEY — and only ever in dev.

It fits what is already shipped: demo mode creates no data-agent service at all (apprunner.tf:121-123), every LLM path is blocked at one choke point (agent_client.py:17-27), and the replay pack already carries the full recorded answer. Artifact URLs become two more recorded fields — and demo_pack.py already writes run_id and recorded_at that load_pack() never reads, so the slot exists.

Verified

Public read-only works, and cheaply

  • permissions.create {type:"anyone", role:"reader"} is the whole call; allowFileDiscovery:false (default) means link-only, not search-indexed.
  • drive.file is sufficient — listed on permissions.create's own scopes. No restricted drive scope, no CASA assessment.
  • A LINKED chart renders for anonymous viewers even when the Sheet is private — it is a cached server-side render, not a live fetch.
  • “Make a copy” works by default (copyRequiresWriterPermission is false), so a read-only visitor can take an editable copy. That is the handover.
  • decided Both the deck and the Sheet go public. The marts are public NSW property records, so a visitor can copy the Sheet and genuinely continue the work rather than receiving a deck they cannot re-derive.
Plan around these
  • A Workspace admin can block type:"anyone" outright — hard 403. A personal Gmail has no such policy layer, which argues for owning the demo artifacts from one deliberately.
  • Normal share links cap near 100 concurrent viewers; publish-to-web via the Revisions resource is the sanctioned fix.
  • The linked-chart behaviour deserves a 60-second smoke test before it is load-bearing: private Sheet, public deck, incognito. NOT_LINKED_IMAGE is the zero-ambiguity fallback.

The Ops dashboard

The awkward conclusion. “Delete all frontend graphing” and “keep an Ops dashboard” are in direct conflict. Either Ops keeps a minimal chart component — in which case some visx survives and the purge is ~90% not 100% — or Ops loses its visuals. My recommendation is the former: retain a deliberately tiny internal-only chart for Ops, and delete everything in the answer path. That is decision D2.

08 · Evals after the purge

More of the harness survives than you would expect

The golden set is also smaller than it looks: the version-controlled pack holds 32 cases, of which only 2 are ready — 30 are un-curated drafts skipped by default. The live dev DB has drifted 9 rows ahead at 41/7. Decommissioning down to three proof questions discards far less reviewed work than the raw count suggests.

G3 — format report_structural_issues() — summary present, every query_ref resolves, insights have heading + body (report.py:14-51) Rebuild This one gates passed (eval_run.py:394). Delete the report and the pass gate has nothing to stand on. Replacement reads deck structure back via presentations.get.

The good news is structural. A Sheet is machine-readable in a way a rendered <svg> never was. Grading currently reaches into in-process objects; after the move it reads cell ranges over an API — which is a better assertion target, because it tests what the user actually receives rather than an intermediate the user never sees.

Consequence of the agent naming layouts: do not grade layout identity. Layout choice is now a model decision, so a golden asserting “slide 2 used Two Charts” is asserting on a coin flip and will flake. The rebuilt G2/G3 should check content presence and shape — a chart exists for the trend, the headline is non-empty, the sheet range holds the expected values — and leave layout identity to the judge, or to a reviewer's eye, where a soft signal belongs.

This is the price of D0, and it is a reasonable one to pay. But it means the three proof goldens verify that the deck is correct, not that it is identical run to run — worth knowing before they are authored.

09 · Build order

Prove it on three questions, then demolish

M0

Deck planner no credentials

Port the content decisions out of compose_pages() into a pure report → DeckSpec planner: which headline leads, which chart carries the argument, what the commentary says. Map units.py classes to Sheets number formats and chart intents to Sheets chart types. Fully unit-testable offline — this is where the real complexity lives.

M1

Template pack v1 + manifest + Pack Inspector

Hand-build five or six named layouts in Slides. A loader reads the pack once via presentations.get, maps displayName → objectId, and caches each chart slot's EMU geometry. Ship a boot assertion so a renamed layout fails loudly rather than producing crooked decks.

Then the Inspector: list every layout with its thumbnail and detected placeholders, toggle which are enabled, and author each “use when” line. Only enabled layouts render into the run workspace's layouts.md. This replaces Template Studio's purpose and is where layout quality actually gets tuned.

M2

Credential + egress boundary security review

One Google refresh token in .env, dev only; prod gets no Google env vars at all. Scopes drive.file + spreadsheets + presentations.

This is the first outbound third-party call from data-agent — new egress for a service whose sandbox blocks sockets outright. It warrants an independent review, not a self-review, and the public-sharing call must be structurally unreachable outside demo mode.

M3

Slide tools + agent orchestration

Register start_deck and add_slide with a per-run counter (max_slides, mirroring SandboxBudgetExhausted). Extend workspace_claude.md with the visualisation phase — which changes the av-* fingerprint, correctly, since the prompt is an optimisation lever. Raise agent_request_limit and agent_total_tokens_limit for the dev runtime, then record the turns actually used so the eventual number is chosen from data rather than guessed.

M4

Three goldens + rebuilt G2/G3

Author three proof questions against the new contract — one single-chart, one multi-slide, one table-led. Repoint G1 at Sheet ranges, rebuild G2 against the deck manifest, and replace G3-format with a deck-structure check so passed has a gate again. Assert on content presence, never layout identity — the agent chooses layouts now, so grading the choice grades a coin flip.

M5

The purge — gated on M4 passing

Only now delete: report-engine, ui/charts, SpecChart, ReportView, pages.py's layout schema, pages_builder, Template Studio, the parity gate and the chart e2e specs. Decommission the old golden set. Retire the visx dependencies.

Do this as its own PR, separate from everything above, so the diff is legible as a deletion rather than tangled with new behaviour.

10 · Risks & failure modes

What will actually go wrong

Cost, not a wall

Loosened budgets hide their own price

Raising agent_request_limit and agent_total_tokens_limit is the right call for a dev-only runtime — but the SDK runtime already ran 26–43 turns against the champion's 18–28, and a visualisation phase compounds that. The cost shows up as latency per answer and spend per eval sweep, not as an error.

Keep the per-tool counters (max_slides) even while the global ceiling rises, so a confused agent produces a short deck rather than a runaway one. Record turns at M4 so the eventual prod number is chosen from data.

Security

Public bypasses RLS, permanently

Every row is RLS-scoped for a reason; an anyone·reader file is outside that model, and a leaked link cannot be un-seen. The guard must be structural — unreachable outside demo mode, the way agent_client.py:17-27 makes LLM paths unreachable. Demo mode already produced an auth-widening finding once.

Coverage

Choropleth has no destination

Maps are not a native Sheets chart type. Explore's choropleth cannot migrate — it either survives on its own renderer, degrades to a ranked table, or the feature goes. Decide deliberately rather than discovering it mid-purge.

Testing

Chart correctness is e2e-only today

There are zero frontend unit tests for any chart component — all 646 lines of coverage are Playwright asserting on DOM. Deleting them removes the only safety net, and the replacement (reading artifacts back over an API) is slower and needs credentials in CI. Budget for that.

Ownership

The pack lives outside git

Layouts are edited in Slides by whoever owns the house style — the point, and the risk. Renaming a layout or nudging a chart slot silently invalidates the cached manifest. M1's boot assertion is what stops a design tweak becoming a production defect.

Non-issue

Network egress

App Runner runs managed public egress (apprunner.tf:2-5) and already reaches the LLM API and Google JWKS. No Terraform change. The boundary question is about the service, not the network.
