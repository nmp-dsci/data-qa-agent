s48 · plan · branch presentation-handover

Template packs: Slides layouts that map to Sheet tables that map to the agent's JSON

The deck path already works on this branch (start_deck / add_slide, a layout loader, a manifest, grader G5, migration 0037). What is missing is the pack: a curated set of Slides layouts, each bound to a Sheet table template with a pre-styled chart, so the agent's per-slide JSON lands in a house-styled deck backed by one Sheet. This plan defines the pack contract, seeds a catalogue for you to curate, adds a change log of what humans edit after handover, and turns that log into the metric the loop improves against.

The one idea

A template is not a slide. It is a triple: a Slides layout (where things go), a Sheet table template (what data shape feeds it, with a chart the curator styled by hand), and a JSON slot list (what the agent must supply). The builder clones the curator's chart spec and swaps the data range. Curation therefore happens entirely inside Google Workspace, and every generated Sheet is a stack of those tables plus a manifest — one file, all the slides' data.

gap

absent

02 · The contract

Three artifacts, one JSON, one mapping

Mapping, made concrete for one layout

agent emits (today's add_slide args, unchanged)
{ "layout": "Headline + Trend",
  "headline": "Median rent in 2077 rose 12.4% in three years",
  "commentary": "Two-bed units drove most of the move.",
  "frame": "rent_by_month",
  "columns": ["month", "median_rent_2br", "median_rent_3br"],
  "chart_type": "line" }
pack binds it (_pack tab row, curated in the Sheet)
layout          | Headline + Trend
enabled         | TRUE
use_when        | One measure over time, 1-3 series.
table_template  | tpl_series        # tab in Pack.sheet
chart_template  | tpl_series!chart1 # chartId cloned
x_role          | first column      # date or ordinal
series_max      | 3
notes_from      | commentary        # speaker notes
placeholders    | TITLE→headline, BODY→commentary
builder does
  1. Append a block to Data tab: title row #3 · Headline + Trend, then addTable named s03_rent_by_month with column types from units.py (date, currency, currency).
  2. spreadsheets.get the pack's tpl_series chart once per run (cached), take its ChartSpec, replace domains[].sourceRange / series[].sourceRange with the new table's ranges, drop extra series beyond series_max, addChart. Colours, fonts, axis format, legend position all come from the curator's chart.
  3. createSlide(layoutId) with placeholderIdMappings, insertText headline into TITLE, commentary into BODY, createSheetsChart (LINKED) into the CHART slot rect, one atomic batch. Second call writes speaker notes (notes need the created slide's speakerNotesObjectId).
  4. Append a row to the Manifest tab: slide index, layout, table name, chart id, headline, frame, SQL query_ref, and a hyperlink to the slide.
gap found

The loader only recognises CHART / TABLE placeholders, which the Slides editor cannot create

load_catalogue() (deck.py:196-206) infers slot geometry from placeholder.type. Slides' theme editor only lets a curator insert text placeholders (title, subtitle, body); CHART and TABLE exist in the API enum but are not authorable in the UI. So a hand-curated pack would yield layouts with no chart slot. Fix in P1: accept a plain shape whose alt-text title is chart, table, kpi or commentary as the slot (the API exposes it as pageElement.title). Curators set it via Format options → Alt text. The _pack tab records which convention each layout uses so the Inspector can flag an unmapped layout.

Why the Sheet template carries the chart

The Sheets API exposes every chart's full ChartSpec through spreadsheets.get. A curator who restyles a chart in the browser (palette, gridlines, axis number format, legend) is editing the spec the builder clones. No chart styling lives in code. This is the single largest "polish" lever and it costs zero Python per iteration.

What add_slide gains

Only two optional fields: frame2 / columns2 for L5, and kpi already exists. Everything else in the table is pack-side. Unknown layouts are still rejected with the curated list, so a bad guess costs a turn, not a deck.

05 · The Sheet

One Data tab, stacked Tables, plus a Manifest

current

One tab per slide

slide1, slide2, … Each tab is a bare range with a chart floating beside it. Nothing says which slide a tab feeds. A human extending the analysis has to hunt.

proposed

Data + Manifest + README

Data      #1 · Headline + Trend       ← title row, hyperlink to slide
          s01_rent_by_month  [Table]  ← addTable, typed columns
          (2 blank rows)
          #2 · Ranked Bars
          s02_growth_by_postcode [Table]
Manifest  slide | layout | table | chart_id | headline | query_ref | sql
README    question, dataset, run id, pack version, "how to extend"

Charts anchor next to their table. Sheets Tables (API GA April 2025) give named, typed, independently addressable blocks, which is what a human-editable single sheet needs. Tabs per slide stay as an option in §08 for very wide frames.

Row cap and width

Frames are already capped at 2000 rows (skills/charts.py:21). A Table block honours that; a frame wider than 26 columns or taller than 2000 rows overflows to its own tab and the Manifest says so. This keeps the "single sheet" promise without pretending every extract fits in a block.

recommended v1

Poll + snapshot diff

  1. A scheduled job (the existing worker/queue path, or a make target for now) lists artifacts from query_runs with artifact_deck_url set and last_seen_version older than Drive's files.get(version, modifiedTime).
  2. For each changed file: presentations.get and values.get on the Data + Manifest tabs, then diff against the stored manifest and the previous snapshot.
  3. Emit typed events into app.artifact_edits (migration 0038): headline_changed, commentary_changed, chart_type_changed, chart_deleted, slide_added, slide_deleted, slide_reordered, table_values_changed, table_rows_added, notes_changed, with before/after text, actor (from Activity API when available), and revision id.
why it makes sense

The edit log is the metric

Nothing else in the loop tells you whether the output was good enough to keep. A deck with zero edits after being opened is a pass. A headline rewritten on every run is a prompt problem. A chart type changed on the same layout three times is a pack problem. The log routes each to the right fix: prompt, pack, or golden.

It also feeds curation the way s21 promoted chat answers: an edited deck can be promoted to a golden with the human's headline as the judge's expected answer text, without touching G1 values.

Guardrails

Read-only scopes already cover this (drive.file sees files the app created). Never write back into a human-edited file. Snapshots store text and structure only, no thumbnails. Polling every 15 minutes for files touched in the last 30 days keeps well inside the 300 reads/min quota.

08 · Build order

Four phases, each usable on its own

P0 · pack v1

Hand-build, then sync (2-3 days, mostly curation)

  • Copy a SlidesCarnival report deck; rebuild the ticked layouts as named master layouts with proper placeholders.
  • Create Pack.sheet: _pack tab + one tab per table template with a styled chart.
  • scripts/pack_sync.py: reads both files, validates (every enabled layout has a bound table, every CHART slot has a chart template, every layout id resolves), writes packs/<name>/pack.json and thumbnails; render_layouts_md() reads pack.json. Curation stays in Workspace; the repo holds a reviewable snapshot.
P1 · builder

Bind + clone (2 days)

  • Single Data tab with addTable blocks, Manifest and README tabs; typed columns from units.py (and fix the sale_count-as-currency bug it exposes).
  • Clone chart spec from the template; speaker notes from commentary; auto-append L9 Sources.
  • appProperties tag {run_id, pack, pack_version}; assert layouts after files.copy.
  • Tests extend test_deck.py with a FakeClient that returns a template ChartSpec.
P2 · inspector

Pack Inspector in Admin (2 days)

  • Lists layouts with cached thumbnails, enabled toggle, use_when, bound table, chart preview.
  • Edits write to the _pack tab via the Sheets API, then trigger pack_sync. Workspace remains the source of truth.
  • Shows per-layout usage and edit-type mix once P3 lands.
P3 · change log

Revision diff + Handover panel (3 days)

  • Migration 0038 app.artifact_edits + artifact_snapshots; poller; differ with unit tests over recorded presentations.get fixtures.
  • Analytics "Handover" panel; ★ promote-edited-deck-to-golden.
  • Eval gate: three goldens with expect_chart, one per shape, pass on pack v1 before merging the branch.

Risks

  • Chart spec clone fragility. Cloned specs reference the template's sheetId in ranges; every GridRange must be rewritten, and any spec field the API rejects on write must be stripped. Pin with a fixture test per template.
  • Refresh-token expiry if the OAuth client sits in Testing status (7 days). Already noted in s47; matters more once a poller runs unattended.
  • Quota. Thumbnails are the expensive read (60/min user); cache per pack version. Pack sync is manual, not on every request.
  • Branch hygiene. Everything from s46/s47 is still uncommitted. Commit the current state first so P0-P3 are reviewable diffs.
