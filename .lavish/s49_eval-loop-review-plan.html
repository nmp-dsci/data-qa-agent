s49 · Evaluation loop review · branch eval-loop-review

Make the eval loop fully traced, judged against goldens, and versioned end to end

The loop is NL → SQL → Python sandbox → Sheets/Slides. Most of the plumbing already exists and has been rebuilt several times (s14, s27, s30, s43, s45, s48). This review checks whether what is there today is solid enough to run an optimisation loop on: every agent action visible in MLflow, an LLM judge that compares the agent's answer to the golden, and a version history you can rewind. It also folds in the learnings from NVIDIA's DABstep write-up and takes a position on the knowledge base.

Thesis

The graders, registry and promotion gate are already good. What is missing is evidence density: the Agent SDK run is a single opaque span, the judge never sees the golden or the deck, the sandbox's stdout and derived frames are thrown away, and a change to the helper library does not change the agent's version. Fix those four, structure goldens as an outcome plus hidden checkpoints, and the same two goldens are enough to prove champion-vs-challenger works.

3 · Target tracing

One trace per run, one span per action, one id joining everything

Whiteboard 2 is the span tree a single run should produce, and the ids that let a golden failure be followed to its exact tool call. The SDK message stream already carries everything needed (sdk_trace.py translates it to the flat trace); the change is to open a child span per translated step instead of only one outer span.

Whiteboard 2 · target span tree and id chain. Every box is a span in MLflow's trace view; the dashed edges are the stored foreign keys.

Spans

Emit a child span from sdk_trace for every model turn and every tool return, with the same attributes the flat trace already carries. Sandbox span gets code_sha, runtime, wall ms, stdout length. Keep the outer span; it is the parent.

Sandbox capture

Extend AnalysisResult with stdout (capped, say 8 KB) and persist the derived frame heads already collected by capture_frames(). Store both in the trace step, not a new table.

Ids

Add otel_trace_id and mlflow_run_id to app.eval_results (migration). The runner already has the query_run id and creates the MLflow run, so this is two columns and two assignments.

Deck manifest

Persist every add_slide call's arguments in slide order (layout, headline, commentary, kpi, kpi_label, frame, columns, chart_type) as query_runs.artifact_manifest jsonb. That is the deck exactly as the agent specified it: template chosen, data and text injected. G5, the judge and the Evaluations tab read from it.

Eval as a span

Grading happens after the run today. Log it as a span on the same trace id (the runner has it) so the MLflow trace shows question → actions → verdict in one view.

MLflow GenAI view

Nothing to build; once child spans exist, the GenAI overview in MLflow 3.12 shows per-tool latency and token percentiles for free (verified in s43).

4 · Golden structure

Outcome golden with hidden checkpoints

The user's question: should a golden carry sub-answers for SQL, Python and Slides, or only the final answer, with the agent free to optimise SQL and Python on its own? Three shapes were considered.

A · Outcome only simplest

Golden = question + expected value(s) + expected deck properties.
  • Agent is free to reach it any way. No leakage possible.
  • A failure tells you nothing about where. The judge must guess the stage.
  • Cannot grade a run whose SQL was right but whose analysis lost precision.

B · Full sub-goldens, all gating brittle

Golden SQL, golden sandbox code, golden slide-by-slide deck, each graded.
  • Precise attribution.
  • Over-specifies: a different but valid SQL, or a different valid layout, fails. s48 explicitly chose not to assert layout identity.
  • Curation cost per golden triples; with 1–2 goldens that is fine, at 30 it is not.

C · Outcome gates, checkpoints diagnose recommended

Golden = outcome (gating) + reference SQL rows, reference frame, reference deck shape (diagnostic only).
  • Pass/fail is decided by G1 (values) + G5 (deck exists, has chart/kpi) + judge-v2 correctness.
  • Checkpoints are compared, scored, and stored, but never gate. They feed the diagnosis field: SQL diverged / analysis diverged / presentation diverged.
  • The agent never sees any of it; it is holdout by construction. Only the offline reflector reads goldens.

Golden v2 shape (extends the existing grader jsonb, no new table)

# evals/cases/nsw_rent.yaml · one case
case_key: nsw_rent-median-weekly-rent-2br-units-postcode-2077-latest-month-s48a1
question: "..."
outcome:                      # GATES
  grader: {kind: scalar, key: postcode, value_col: median_weekly_rent, tolerance_pct: 1}
  artifact: {min_slides: 2, expect_chart: false, expect_kpi: true}
  answer_text: "Median weekly rent for 2-bedroom units in 2077 was $606.92 in ..."   # judge reference, label high
  label: high
  calibration_examples:        # optional, curator-written; the judge must reproduce these labels
    - {label: medium, answer: "Rent in 2077 is about $600 a week."}
    - {label: low, answer: "Rents rose across Sydney last year."}
checkpoints:                  # DIAGNOSE ONLY, never shown to the agent
  sql: {golden_sql: "...", rows_sha: "…", key_cols: [postcode, month]}
  analysis: {frame_sha: "…", derived_cols: [median_weekly_rent], expected_skills: [latest_value]}
  deck: {layouts_any_of: [L1, L2], kpi_label_contains: "rent"}
holdout: true

The existing columns map directly: golden_sql → checkpoints.sql, golden_sandbox → checkpoints.analysis, golden_objects/golden_report → checkpoints.deck, grader → outcome.grader. The runner's golden_truth() already re-runs golden_sql live, so rows_sha is computed at eval time, not stored.

5 · LLM-as-a-judge v2

One judge, ordinal labels, calibrated on the golden set first

What it sees new

Question, the golden's answer_text and expected values, the agent's answer text, the deck as the agent specified it (each add_slide's layout, headline, commentary, kpi, chart type, rendered as a compact outline), and the G1 numeric verdict. Every input is something the agent chose or the golden defines; nothing is hidden from the judge.

What it returns

label: low | medium | high for the answer against the golden, diagnosis: sql | analysis | presentation | knowledge | none, and one sentence. Three ordinal levels, not a 0–10 score: labels are what a curator can assign consistently, and what the goldens carry, so judge and golden speak the same scale. The diagnosis is cross-checked against the checkpoint scores.

Model

sonnet-5 at medium effort, the same model and runtime as the agent. The cross-family rule is dropped; everything runs on agent_sdk. Rubric text is hashed as before and versioned label-v1. One line of caution: a same-model judge has a known self-preference bias, which is why the calibration step below is mandatory rather than optional.

Calibrate on goldens first

Before scoring any agent answer, the judge scores the golden set itself: each golden's answer_text must come back high, and any curator-written calibration_examples must come back with their stored labels. A judge that cannot reproduce the golden labels does not score the run; the eval is marked judge_uncalibrated.

Gating advisory until 10 goldens

A case passes on G1 and G5 only. The judge label and diagnosis are recorded on every eval row and shown in the Evaluations tab but do not gate until the pack reaches 10 goldens (the runner's existing HOLDOUT_MIN_CASES). The old insight judge is removed; its rubric hash stays on historical eval rows only.

6 · DABstep learnings applied

NVIDIA's three-phase split, mapped onto what exists here

The write-up's result: 89.95% on hard tasks at 20s per task versus a Claude Code baseline of 66.93% at 10 minutes. The mechanism was not a better model. It was moving reasoning offline into a tested helper.py, then giving the fast inference agent only function signatures and a short prompt. Three phases: a heavyweight learning loop that discovers shared sub-operations across tasks and refactors them into helpers; fast single-pass inference importing those helpers; offline reflection that audits solutions and feeds prompt fixes back.

The skill-miner must therefore be gated on holdout the moment the pack passes 10 cases, and until then every proposed helper is a human-reviewed PR, not an auto-merge.

7 · Knowledge base: filesystem markdown or Agent SDK skill?

Opinion: keep the markdown filesystem for facts, use one SKILL.md for procedure

Markdown filesystem keep

  • Already a 3-tier disclosure system: index → search → read (knowledge.py:147-260), with lint() and a generated INDEX.md.
  • Content-hashed into knowledge_version and the fingerprint. Versioning is free.
  • Copied into the per-run workspace; the agent greps it with Read/Grep under a quota hook (sdk_agent.py:668-722). Reads are metered and provenance-tracked.
  • Facts change per dataset. Pages are the right unit for a curator to edit.

Agent SDK skills not for facts

  • A SKILL.md is loaded by description match when the model decides it is relevant. That is procedural knowledge: "how to answer a growth question", not "what a bedroom band is".
  • No index, no search, no lint, no read quota. Everything knowledge.py gives you would be rebuilt or lost.
  • Skill discovery depends on the SDK's setting_sources and cwd; the per-run workspace already controls both, so a skill would work, but it adds a second discovery mechanism next to the existing one.

What to change

  • Split by kind, not by mechanism. Domain facts and presentation rules stay as knowledge/**/*.md. The single procedural document, CLAUDE.md, gains an auto-generated "skills available" block from the @skill registry (section 6). If you later want the SDK's on-demand loading for long procedures, add exactly one skills/analysis/SKILL.md that describes the helper library; keep it generated.
  • Give knowledge a curator write path that mirrors ordinals: app.knowledge_pages (path, body, version, author, created_at) with an append-only log, an admin PUT, and make knowledge-export that writes rows back to services/data-agent/knowledge/ for a commit, the same pattern eval_pack.py uses for goldens. The workspace loader prefers the DB row when present. Section 8 says why the export step matters.
  • Keep the read quota. Six page reads per run is a real cost control and a diagnosable signal (knowledge_pages_used).

8 · Version control for the loop

One agent bundle, reconstructible from its fingerprint

Whiteboard 4 · version lineage. A rewind is: read bundle.json from the MLflow version, check out its git sha, restore the two DB snapshots it names.

Rules

  • Add skills_hash to build_sdk_fingerprint(). This is a one-line fix with a large consequence: every helper change becomes a challenger.
  • On make mlflow-register, upload bundle.json (component → hash, git sha, image tag, DB snapshot ids) and a tarball of prompts/, skills/, knowledge/ to the model version. Sizes are tiny.
  • Curator edits in the DB (ordinals, future knowledge pages) are exported to git and committed before a register. A version is never "git sha plus unknown DB state".
  • Rubric hashes (jr-…) and the pack version are recorded on the eval run, not the agent version. They are the ruler, not the thing measured.

Time travel

make agent-checkout FP=av-3f2a1b9c0d4e
# → reads bundle.json from MLflow
# → git worktree add .worktrees/av-3f2a… <sha>
# → restores knowledge + ordinals rows named in bundle.json
# → prints the compose override to run it as a challenger

This is the operation that makes "what did the agent know when it answered run X" a command rather than an archaeology exercise. It is also what the reflector uses to reproduce a failure.

9 · Champion vs challenger on two goldens

Proving the system, not the agent

A challenger is any new fingerprint. With sections 3 to 8 in place, the end-to-end proof is this sequence, and it needs no more goldens than exist.

1

Baseline the champion

The judge first reproduces the golden labels (section 5). Then make eval 3 repeats on the 2 ready goldens; the judge label agrees with G1 on 6/6. Every run has child spans in MLflow.

2

Mint a challenger by editing one helper

Change skills/analysis.py (for example a stricter latest_value). Fingerprint changes because skills_hash is now a component. make mlflow-register uploads bundle.json.

3

Eval the challenger

Same pack version, same rubric hash. make eval EXPERIMENT=… stamps hypothesis and base_run_id, which the Evaluations tab already renders as a gate badge.

4

Promote or hold

make promote: eval accuracy versus the champion, and nothing else. Pass-rate ≥ champion's on the same pack version and zero pass→fail flips, computed from G1 and G5. The judge label is reported alongside, advisory. The rule in mlflow_registry.py:230-233 is unchanged.

5

Rewind

make agent-checkout FP=<old champion> reproduces a run bit-for-bit on prompts, skills and knowledge. If that works, the loop is version controlled.

Runtime note. Prod is demo mode with no data-agent service, so all of this is dev and CI only, as s43 and s45 already decided. Nothing in this plan touches prod.

Order and effort

  • One PR for M0–M5 (D5). Build order inside it: M0+M1 first (observability and versioning foundation), then M2 (golden contract), then M3 and M4 in parallel, then M5.
  • M5 runs the whole loop, including the offline optimiser, against two made-up golden question/answers authored for the test, not the existing three.
  • Rough sizing: M0 2 days, M1 1 day, M2 2 days, M3 3 days, M4 2 days, M5 half a day.

Risks

  • Span volume. Per-turn spans on a 40-turn run is fine for sqlite MLflow at this scale; revisit if the pack grows past 50 cases.
  • Judge self-preference. Same model judges its own output. Mitigated by the mandatory golden-label calibration and by G1 staying primary.
  • Overfitting the helper library to 2 goldens (section 6 caution). Mitigated by human-reviewed PRs and the 10-case holdout floor.
  • O-2 duplication means every sandbox contract change is done twice. M0 touches it; a follow-up could generate the pyodide bootstrap from runner.py.
