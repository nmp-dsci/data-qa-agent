The short version

The database is already "off" when idle — Aurora Serverless v2 is at min 0 ACU with a 1 h auto-pause. What you were paying for is the backend's own demo janitor waking it four times a day (main.py:66-93 — now removed, uncommitted) and the plumbing that exists only because there is a database at all: a public IPv4, 12 Secrets Manager secrets, the ECS migrate/pipeline jobs, the VPC.

Two honest levers. A 10-line fix ships today and takes data-qa from ~$36 to ~$17/mo. Getting to the transcript-rag-agent shape (~$5/mo, no cold-start hang, 5-minute deploys) means cutting the DB out of the demo path: SQL editor and Explore become dev-only, the goldens/evals/ops exhibits become a static JSON dump in S3, and the demo user stops being a database row — about a day. "Stop the cluster" is not a real option: RDS auto-restarts it after 7 days and the demo login breaks on the first visit.

2 · Why Aurora is awake

A 6-hourly heartbeat, not visitors

CloudWatch ServerlessDatabaseCapacity, hourly, Sept 1–22: the cluster wakes at ~00:55, 05:55, 11:55 and 17:55 UTC every single day, weekends included, then stays up for the full 1 h seconds_until_auto_pause window. Each wake burns ~0.6 ACU-h; four a day ≈ 2.5 ACU-h ≈ $0.50/day ≈ $15/mo.

The source: services/backend-api/app/main.py:66-93

_DEMO_RESET_INTERVAL_S = 6 * 3600

async def _demo_reset_loop():
    while True:
        try:
            # RLS trap: look the demo user id up first …
            async with rls_connection(None) as conn:
                demo_id = (await conn.execute(text(
                    "SELECT id FROM app.users WHERE username = :u"), …)).scalar()
            if demo_id is not None:
                async with rls_connection(str(demo_id)) as conn:
                    await conn.execute(text(
                        "DELETE FROM app.conversations WHERE user_id = :uid "
                        "AND created_at < now() - interval '24 hours'"), …)
        except Exception as exc:
            log.warning("demo reset skipped: %s", exc)
        await asyncio.sleep(_DEMO_RESET_INTERVAL_S)   # ← wakes a paused Aurora 4×/day

The janitor was designed as an in-process singleton so demo deployments wouldn't need EventBridge — correct — but it runs whether or not anyone has used the demo, and each run resumes a paused cluster, which then bills for the next hour.

Done — janitor removed, sweep moved into demo-login uncommitted

  • main.py — _demo_reset_loop, its 6 h interval and the lifespan task are deleted. Nothing in the process touches Postgres on a timer any more.
  • routers/auth.py — demo_login now calls _sweep_demo_conversations(user_id) after minting the session: the same 24 h DELETE FROM app.conversations, run as the demo user (RLS trap preserved), throttled to once per 6 h, fail-soft so housekeeping can never break a login.
  • Net effect — a visitor has already woken Aurora when the sweep runs, so it costs nothing extra; an idle demo never wakes the cluster. Ruff, mypy and the backend suite (109 passed) are green.
  • Optional next — pause window 3600 → 900 s in aurora.tf; not applied yet (trade-off: more ~15 s cold starts for first visitors).

Expected once deployed: Aurora compute $15 → ≈$2.50 (deploys + a handful of real visits). I/O $3 → ≈$1.50. About $14/mo for ~10 lines of Python and one terraform number.

"Stop" is not "off". aws rds stop-db-cluster is allowed on Aurora but RDS automatically restarts it after 7 days, storage keeps billing, the public IP keeps billing, and the first visitor gets a 500 on demo-login. It would save ~$15/mo for one week at a time and then silently come back. Not a plan.

Destroy needs a snapshot first. aurora.tf:64-65 sets skip_final_snapshot = true and deletion_protection = false. A terraform destroy of the cluster loses the curated goldens, eval history, promotions audit and knowledge pages that only live in app.*. A manual snapshot of the 2.4 GB volume costs ≈$0.05/mo to keep. Option C includes it as step 0 — nothing gets destroyed without your explicit go.

5 · Option C blueprint

What "like transcript-rag-agent" means for this codebase

Target terraform — infra/terraform/demo/main.tf

Mirrors transcript-rag-agent/infra/terraform/demo/main.tf: ECR repo + lifecycle (keep 5) · IAM role for ECR pull · one App Runner service 0.25 vCPU / 512 MB with DEMO_MODE=1 baked into the image · one 5xx alarm · the existing S3 + CloudFront frontend, which also hosts the exhibit dump.

Removed: aurora.tf, network.tf (VPC, subnets, IGW, 3 security groups), secrets.tf (7 random passwords, 12 secrets), ecs.tf (cluster, 2 task definitions, 3 roles), the App Runner instance role and its policies, moved.tf, the ops CloudWatch grant. deploy-aws.yml loses the migrate/pipeline/settle-wait steps.

Exhibits: one export, served from S3

A make export-exhibits script reads the goldens, eval runs (incl. the s51 case drill-downs), promotions/registry, ops rollup and architecture payloads through the existing read endpoints and writes them as JSON under exhibits/ in the frontend bucket. In demo mode the frontend's API client resolves those routes to the static files instead of the backend — the tabs render exactly as today, frozen at export time. Re-export whenever the local eval loop produces something worth showing.

SQL editor and Explore keep their Postgres implementation for make up; the demo nav simply doesn't show them (App.tsx:111-115 already gates tabs by auth mode).

6 · Account-wide extras

Independent of the database decision

Auto-deploy flag — $4/mo

All four App Runner services pay $1/mo for the ECR-push trigger. Each deploy workflow already pushes the image; replacing the trigger with aws apprunner start-deployment in CI removes the charge and makes the deploy step explicit. One-line change ×4 repos.

ECR history — ~$1.3/mo

data-qa/data-agent 25 GB and data-pipeline 15 GB of images the current deployment never pulls; ap-southeast-1/tau2loop-demo is a repo with no service. A "keep last 3" lifecycle policy on each is enough.

Singapore vs Sydney

dabstep and convfinqa run in ap-southeast-1, the others in ap-southeast-2. No cost difference, just two regions to remember when listing services. The billing alarm (data-qa-billing-over-50usd) is account-wide and is currently sitting just under its threshold.
